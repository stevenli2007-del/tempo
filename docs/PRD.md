## 1. 产品定位（对齐总蓝图）

**一句话定位**：Tempo 是学生的课程操作系统（Course OS）——它不只整理你的课程信息，而是**持续检测各数据源的变化、动态更新你的进度、并据此规划你每天该做什么**。

**北极星原则**：每一个功能都要问——这是不是在替学生消化"元工作"？不服务于这条原则的功能不做。

**内核优先于表层**（总蓝图原则 6）：翻译整理 syllabus 是让学生第一次觉得有用的**入口**；真正让学生每天打开、并且离不开的，是"实时检测 → 动态管理 → 动态规划"这条闭环。当"做一个漂亮的整理功能"与"让同步更及时更可靠"冲突时，**永远选后者**。

**为什么现在做（蓝海判断，一句话版）**：学生目前的替代方案是"手动问 ChatGPT + 四处找资料 + 手动维护 Notion"，非常麻烦且不会自己更新；难的不是界面，是**数据接入深度**——这恰好是个人项目能做、大厂看不上的窗口。完整论证见总蓝图「为什么是蓝海」章节。

## 2. 目标用户与种子用户

### 2.1 目标用户画像

伯克利在校学生，每学期同时修 3-6 门课。核心痛点不是"找不到 deadline"（Canvas 打开就能看到），而是：

- 课程规则散落在 syllabus 的 PDF 里，每学期要重新搞懂一遍
- deadline 散在 Canvas、Gradescope、Piazza 等多个平台
- **deadline 会变**，需要反复去各个平台确认有没有改
- 不知道"今天到底该先做哪件事"

### 2.2 Phase 0 种子用户（5-6 人）

> 种子用户不是营销问题，是**验证设计问题**——前 5-10 个人是谁，直接决定验证出来的结论是否可信。



| 类型                | 建议人数  | 验证什么                                   | 注意                         |
| ----------------- | ----- | -------------------------------------- | -------------------------- |
| **技术型**（CS / 工程）  | 2-3 人 | 内核价值：同步是否靠谱、延迟是否可接受                    | 反馈会偏技术视角，不能全听              |
| **非技术型**（文科 / 社科） | 2-3 人 | 表层与门槛：syllabus 解析是否有感、token 粘贴这步能否跨过   | **关键样本**——若他们卡在授权步骤，说明门槛过高 |
| **跨课型差异**         | 尽量覆盖  | 不同课程的 syllabus 结构差异（有无明确考试日期、评分构成是否复杂） | 避免全是同一类课程的 syllabus        |

**要求**：至少覆盖 2 门以上不同学科的课程；至少 1 人有"课程平台不止 Canvas"的情况（用于观察数据源差异）。

> 具体名单待定，见 `Decisions.md` 待决事项 O-02。

## 4. Phase 0 目标与里程碑

**Phase 0 要验证的两个核心假设**：

1. **表层假设**：学生愿意上传 syllabus，且认为 AI 解析结果比自己啃 syllabus 更省心。
2. **内核假设**：数据源自动同步 + 进度自动更新，确实减少了学生打开 Canvas 确认信息的次数。

### 4.1 里程碑拆分（按顺序交付，逐个验收）

| 里程碑           | 范围                                                            | 验证假设 | 依赖风险                  |
| ------------- | ------------------------------------------------------------- | ---- | --------------------- |
| **M1 — 静态理解** | F1 账号 + F2 Workspace + F3 syllabus 解析 + F5 总览页（仅 syllabus 数据） | 表层假设 | 低，无外部依赖               |
| **M2 — 动态感知** | F4 数据源同步 + F6 凭据管理 + F5 总览页（合并 Canvas 数据）                     | 内核假设 | 中，依赖 Canvas token 可用性 |

**为什么拆两段**：M2 涉及加密存储、服务端代理、token 过期提醒、同步失败降级，出错面远大于 M1。若 Canvas PAT 路线被证伪（学校关闭学生 token 入口），M1 的核心验证不受拖累，iCal Feed 作为 Plan B 顶上（见 [ADR-002](./Decisions.md#adr-002)）。

## 5. Phase 0 功能详情

### F1 用户账号

- 邮箱 + 密码注册/登录（Google OAuth 登录作为增强项，非必须）
- 登录后进入个人总览页

**验收标准**：新用户可注册并登录，看到空态总览页（无课程时显示"新建第一个课程"引导）。

### F2 Workspace（课程空间）管理

- 创建课程 Workspace：**必填** Semester（如 "Fall 2026"）、课程名称（如 "Math 53"）；**选填** 课程编码、教师姓名
- 课程列表按学期分组展示
- 支持编辑/删除课程

**验收标准**：填写学期与课程名后生成课程卡片，出现在总览页与课程列表中。

### F3 Syllabus 上传与结构化解析（M1 核心）

- 每个 Workspace 内有"上传 Syllabus"入口，支持 **PDF / .docx / .pptx**
- 系统提取文本后，调用 LLM 抽取五个结构化板块：
  1. **Grade Composition**：成绩组成项名称 + 占比
  2. **Course Outline**：章节/周次 + 主题
  3. **Test Dates**：考试名称 + 日期 + 时间 + 地点（缺失时显示 **TBD**，**禁止编造**）
  4. **Office Hours**：负责人 + 星期 + 时间段 + 地点/链接
  5. **Submission Policy**：提交方式描述 + 涉及平台名称
- 解析结果进入**可编辑表单**，用户核对/补全/覆盖后保存，成为该课程的权威信息
- **修正数据必须存成 diff**：同时保存"原始解析结果"与"用户修正后结果"及差异字段，作为后续优化 prompt 的种子数据。**只存最终结果 = 将来一堆没法用的散数据**
- **降级**：若文本提取失败（扫描件/复杂排版），明确提示用户"这份文件我们读不出来，请手动补充关键信息"，**不静默返回空、不猜测填充**

**验收标准**：上传真实 syllabus 后 10-30 秒内看到五个板块结果（哪怕不完全准确），可逐项编辑，保存后 Workspace 页展示最终信息。

### F4 数据源同步（M2 核心，Tempo 内核的第一环）

- **主路径 — Canvas Personal Access Token**：
  - 设置页粘贴用户在 bCourses 生成的 token，附图文教程
  - 服务端用该 token 拉取 Canvas 课程列表与作业（含 due date）
  - **请求一律在服务端发起**，token 加密存储，绝不暴露给前端
  - ✅ **入口已实测可用**（P0-2-1，2026-09-01）：bCourses Settings 中 "+ New Access Token" 存在，PAT 路线成立
- ~~**Plan B — Canvas Calendar Feed（iCal）**~~ ⏸ **不进 Phase 0**：仅在学校将来关闭 token 入口时启用，作为长期 Plan B 保留（[ADR-002](./Decisions.md#adr-002)）
- **课程关联**：用户手动将 Canvas 课程与 Tempo Workspace 关联（不做自动匹配，避免匹配错误；Phase 1 再引入匹配辅助）
- **刷新机制**：提供手动刷新按钮 + 后台定时轮询（**前期频率放宽，优先保证数据新鲜度**；具体数值见 [`Sync-Strategy.md`](./Sync-Strategy.md)，策略依据 [ADR-005](./Decisions.md#adr-005)）
- **失败可见性（硬性要求）**：同步失败必须在 UI 明确提示，展示"最后一次成功同步时间 + 失败原因"，**绝不允许静默展示过期数据**——静默的旧数据比明确的错误更危险
- **Token 有效期**：学生 token 的过期时间为**强制填写**，当前上限约 120 天（政策在收紧，可能变化）。系统须基于**用户实际填写的过期时间**提前提醒，而非写死固定天数
- **撤销授权入口**：用户可随时断开 Canvas 授权并删除已存凭据

**验收标准**：粘贴 token 后能看到 Canvas 课程列表；手动关联某课程后，该课程近期作业与 due date 出现在任务列表中；总览页显示最后同步时间；断网或 token 失效时显示明确错误提示而非旧数据。

### F5 总览页

- 课程卡片列表：每张卡片显示课程名 + 近期即将到期的 1-2 个任务
- 跨课程"近期任务"列表，按日期从近到远排序，**合并** syllabus 考试日期与 Canvas 作业 due date
- **同步状态指示**：显示"最后同步时间"（M2）——这是信任的关键 UI 元素

**验收标准**：登录后能看到"最近 7 天内所有课程要做的事"，可点击跳转到对应 Workspace 详情。

### F6 设置与凭据管理（M2，隐私最小交代）

Phase 0 就要给用户一个交代，不要等合规阶段再补：

- **我的数据"页面（或设置页区块）**：说明存了哪些数据（syllabus 原文、解析结果、Canvas 凭据、任务数据）
- **一键删除 Canvas 凭据**
- **一键删除账号及全部数据**（含级联删除所有课程、任务、上传文件）
- **隐私说明（简洁版）**：数据存在哪、用于什么、不会分享给谁

> 依据 [ADR-008](./Decisions.md#adr-008) 的风险分级，以及总蓝图原则 5「学校关系是战略资产」。完整方案见 `Security-Privacy.md`。

## 6. 冷启动设计：30 秒内看到价值

从注册到看到价值，链路过长（注册 → 建课 → 上传 → 等 10-30 秒解析 → 关联 Canvas → 才看到东西），中间任何一步卡住就流失。

**Phase 0 必须做的两件事**：

1. **Demo Workspace**：注册后可选"先看看效果"，系统预置一份示例课程（含已解析好的 syllabus 与示例任务），用户**立刻**看到总览页长什么样，再决定要不要建自己的课。
2. **解析过程可视化**：上传后不要让用户干等——先展示"已提取的文本预览"（几乎立刻可见），再逐步填充五个板块，并用进度提示（如"正在解析考试日期…"）。

**验收标准**：新用户从进入站点到看到"有内容的总览页"，Demo 路径不超过 30 秒。

## 7. Phase 0 明确不做的事（Non-Goals）

| 不做                         | 原因                                                                           |
| -------------------------- | ---------------------------------------------------------------------------- |
| CalCentral 集成              | 学校账号认证 + 无公开 API，投入产出比不匹配（[ADR-007](./Decisions.md#adr-007)）                 |
| Canvas OAuth 正式接入          | 需伯克利机构审批，留 Phase 1（[ADR-002](./Decisions.md#adr-002)）                        |
| 代替用户提交作业（Gradescope 自动提交等） | B2 高风险类，失败后果直接影响学业，仅作长期 opt-in 实验，不进主流程                                      |
| 每日任务智能排序 / 自动分解            | Phase 2 的事。Phase 0 只**按时间顺序**把任务摆出来                                          |
| 资源 Hub / past paper 共享     | Phase 4，且涉及**真正的法律风险**（UGC 版权），与 Canvas PAT 的 ToS 风险性质不同                     |
| 移动端原生 App                  | 先做响应式网页，手机浏览器可用即可                                                            |
| 多数据源并发接入                   | Phase 0 只接 Canvas 一条（+ iCal 作 Plan B），CalCentral / Google Calendar 留 Phase 1 |

## 8. 成功标准

### 8.1 量化指标

| 指标              | 定义                                  | 目标        | 验证的假设                              |
| --------------- | ----------------------------------- | --------- | ---------------------------------- |
| **编辑修正率**       | 上传过 syllabus 的课程中，用户主动编辑/修正过解析结果的比例 | ≥ 50%     | "AI 解析 + 人工核对"闭环真的在发生（而非用户看都不看就保存） |
| **7 日回访次数**     | 关联数据源后 7 天内主动打开总览页的次数               | ≥ 3 次/人   | 内核价值：自动同步是否减少了打开 Canvas 的次数        |
| **人均关联课程数**     | 完成数据源关联的课程数量                        | ≥ 2 门     | 接入门槛是否可接受                          |
| **token 续期完成率** | 收到过期提醒后完成重新授权的比例                    | 观察项（不设目标） | "手动授权"这个摩擦的长期可接受度                  |

### 8.2 定性判断

- 用户主观反馈"确实减少了打开 Canvas 确认信息的次数"
- 用户愿意为下学期继续用（**留存意愿是最真实的信号**）
- 用户会主动提出"能不能再接 XX 平台"（说明内核价值被感知到了）

## 9. 关键用户旅程

**主路径（新用户）**

1. 注册 → 看到 Demo Workspace（30 秒内看到价值）→ 决定自己建课
2. 新建第一个 Workspace（学期 + 课程名）
3. 上传 syllabus PDF → 看到文本预览 → 五个板块逐步填充 → 逐项核对修改 → 保存
4. 去设置页粘贴 Canvas token → 拉取课程列表 → 手动关联到刚建的 Workspace
5. 回到总览页 → 近期任务里同时出现 syllabus 考试日期与 Canvas 作业 due date → 看到"最后同步时间"
6. 重复 2-5，添加第二、第三门课
7. 每天打开总览页，一眼看到所有课程近期要做的事，不用分别打开各个课程系统

**异常路径（必须同样可用）**

- 上传扫描件/复杂排版 syllabus → 明确提示读不出 → 用户手动补充关键信息 → 流程继续
- Canvas token 失效/过期 → 总览页显示"同步失败 + 最后成功时间"，引导重新授权（**这是必然发生的路径**，约 120 天一次）
- ~~Canvas token 入口被学校关闭 → 引导改用 iCal Feed（Plan B）~~ ⏸ 低概率，P0-2-1 已确认入口可用；真发生则走长期 Plan B

这个旅程（含异常路径）走通，就是 MVP 成功验证的标志。

## 10. 风险与预期管理

| 风险                   | 性质              | 等级      | 应对                                 |
| -------------------- | --------------- | ------- | ---------------------------------- |
| Canvas token 入口被学校关闭 | **平台政策（ToS）**   | 低（✅ P0-2-1 已确认当前可用） | iCal Feed 作长期 Plan B；Phase 1 走 OAuth |
| Token 过期导致同步中断       | 产品体验（**非合规问题**） | 高（必然发生） | 基于用户填写的过期时间提前提醒 + 失败可见性            |
| 同步延迟导致错过 deadline    | 产品可信度           | 高       | 前期放宽轮询频率；总览页显示最后同步时间；失败显式提示        |
| AI 解析编造考试日期          | 产品信任            | 高       | 强制 TBD 状态 + 禁止编造 + 用户可编辑覆盖         |
| 种子用户全是技术党导致反馈偏差      | 验证有效性           | 中       | 种子用户构成强制混合（见 2.2）                  |
| 用户数据存储在 Supabase 的顾虑 | 信任 / 隐私雏形       | 中       | Phase 0 就给隐私最小交代 + 一键删除（F6）        |

> **风险分级原则**：平台政策（ToS）风险与法律风险是**两类不同量级**的问题，不可混谈。Canvas PAT 属前者（最坏后果是 token 被撤销）；Phase 4 的 UGC 版权 / FERPA 属后者。详见 [`Security-Privacy.md`](./Security-Privacy.md) 与 [ADR-008](./Decisions.md#adr-008)。
