# P0-3-35 · 总览取数：已完成的历史不该吃掉窗口（+ 重复考试行诊断）

> 新开 2026-09-23。🔴 **这是 P0-3-13 freeze 前的显式例外**：
> `Roadmap.md` §9.4 写的是「3-13 freeze 后不追加卡片」，而第二批六张（29~34）收官时
> 也写过「六张之后不再追加」。本卡之所以破例，是因为它**不是新功能，是数据准确性 bug** ——
> 总览页少显示任务，直接打脸产品命根「实时检测」与 G0-8（人工干预率）。
> Steven 2026-09-22 拍板：**质量修复可以插队，新功能不行**。

---

## 1. 它修什么（症状）

2026-09-21 截图：总览页「接下来 7 天」日历全空、待办清单只剩一场考试，
而顶部写着「已完成 49 项」—— 明明还有一堆作业没显示。

**同步是好的**（截图顶部「Canvas 已于刚刚同步」）。坏的是**取数**。

### 根因（探针实测，不是推断）

`lib/tasks.ts` 的 `loadTasks()` 时间过滤**只有上界**（`due_date <= now+7d` 或 null），
排序又是 `due_date` **升序** → 最早的排最前。一学期积下来的**已交作业整队占满前 50 位**，
把 `limit`（当时 50）吃光。

`scripts/probe-task-window.ts` 2026-09-23 实测（limit 50）：

| | 旧取数 | 新取数 |
|---|---|---|
| 已完成且早于下界 | **35** | 0 |
| 未来到期（now 之后） | **0** ← 症状 | **14** |
| 逾期未完成 | 1 | 1（不变） |

「未来到期 0 条」就是 Steven 看到的现象的硬证据。

## 2. 修法

### ① 给**已完成**的行设时间下界，未完成的不动

新 `loadTasks({ historySince })`：排除「已完成 **且** 截止日早于下界」的行。

- **未完成的行（含逾期未交）一律保留** —— 逾期未完成是总览页最该被看见的信号，
  给它设下界等于帮用户逃避，与 Tempo「不隐藏问题」冲突。
- 下界由总览页传：`now - 7 天`，按**学校日历日**回退（`addDays(schoolDayKey(now), -7)`），
  与周历同一套日键口径，夏令时切换不差一天。
- `GET /api/v1/tasks` **不传** —— 那是带 `offset` 翻页的数据接口（契约 §5），
  翻页能取到全部历史，设下界反而是丢数据。

SQL 侧拆成**两条** `or()` filter（多次调用是 AND）：

```
① or=(status.neq.done, due_date.gte."since", due_date.is.null)
② or=(submission_state.is.null, submission_state.eq.<未完成态…>, due_date.gte."since", due_date.is.null)
```

三条容易踩的坑（都实测过）：

- 🔴 **② 必须用正向 `eq` 枚举「未完成态」补集**，不能写 `neq.submitted,neq.pending_review,neq.graded`。
  `NOT(S=a OR S=b)` 展开是**合取**（S≠a **且** S≠b），而 `or()` 串里各项是**析取** ——
  写成三个 `neq` 后，一条 `S='submitted'` 的行会因为满足 `neq.pending_review` 而被保留，
  整条 filter 退化成恒真。第一版就错在这里：加完仍有 16 条历史没排掉。
- 🔴 **`submission_state.is.null` 必须留在 ② 里**：`null` 的行（**考试派生 + 手动任务**）
  的 null 表示"与 Canvas 无关"，不是"Canvas 判定未完成"，漏了会被整批静默删掉。
- 🔴 补集**从全量枚举减出来**（`TASK_SUBMISSION_STATES` − `CANVAS_DONE_STATES`），不手抄。

### ② `CANVAS_DONE_STATES` 提成常量（唯一来源）

SQL 侧要拼「哪三个态算完成」，界面侧 `isCanvasDone()` 已经有一份 ——
**两处各写一遍就是下一次 P0-3-15**（加一个态 → SQL 与界面口径悄悄打架，而三道门禁全绿）。
所以常量落在 `lib/tasks/progress.ts`，两边都读它。

### ③ 安全上限 50 → 200 + 溢出文案改如实

排除历史后窗口仍可能过百（重度周），上限不该再当第二道铡刀。
原溢出文案「其余在下方清单里」是**假的** —— 超出上限的行既不在日历里、也不在清单里
（清单用的就是同一批取回的数据）。改成「窗口内共 N 条，页面用的是取回的前 M 条」。

### ④ 已完成折叠盒的标签改「最近已完成 N 项」

数字含义从"学期累计"变成"近 7 天"，标签不写明的话，用户只会看到 49 掉到 12 而不知道为什么。

## 4. 验收标准

1. `probe:task-window`：旧取数里存在"已完成的历史"，新取数里**必须为 0**；
   单跑 ① / 单跑 ② 各剩一些、合起来 = 0（证明多次 `or()` 是 AND，不是被静默忽略）。
2. 新取数的**未来任务数 ≥ 旧取数**（修的是"未来被挤掉"）。
3. 新取数的**逾期未完成数不小于旧取数**（下界没误伤未完成）。
4. `tsc` ✓ / `eslint` 0 error / `build` ✓ / 全部回归全绿 / 三把文档闸门全绿。
5. 肉眼：总览页「接下来 7 天」有未来作业；「最近已完成 N 项」数字合理（不是 49）。

## 5. 诊断附带结论：重复考试行（**待 Steven 拍板才动数据**）

`probe:exam-duplicates.ts` 只读跑了全量 `exam_dates`（18 行 / 13 组），两类发现：

### ① 「两个 Midterm 1」是我上次看错了 —— 不是重复

Physics 7A Midterm 1（9/28）与 MATH 53 Midterm 1（10/1）是**两门不同的课**，
同名≠重复。上次诊断说"匹配失败留下重复行"，此说已作废。

### ② Math 53 Discussion「Quiz」×6 —— **合法，不合并**

一条 syllabus 句子列了 6 个 quiz 日期（9/4、9/18、10/16、10/30、11/20、12/4），
被拆成 6 行**同名**考试。删掉任何一行都等于丢一个真实考试日。
⚠️ 副作用：改期时 `resolveExamTargets()` 会判「多命中」→ 不写（这是 P0-3-29 的既定纪律，正确）。

### ③ Chem 1A 9/22 真有一对重复 —— **建议删，但等你点头**

| id | 名字 | source | created | location |
|---|---|---|---|---|
| `8ee6328b…` | Unit 1 Exam | syllabus | 2026-09-13 | null |
| `063f6a4a…` | Chem 1A exam | manual | 2026-09-22 | null |

同一门课、同一天、名字不同（`unit1exam` ≠ `chem1aexam`，按名归一抓不到）。
来源是一条座位公告「Your seating assignment for tomorrow night's Chem 1A exam (Sep 22)」——
名字是通称 → 匹配 0 命中 → 走了 insert（正是 Steven 说的"应该更新而不是新建"）。

- **建议**：删 `063f6a4a`（manual 那行），保留 `8ee6328b`（syllabus）。
  两行的 `location` / `exam_time` **都是 null**，删它不丢任何信息。
- 🔴 **未删**：删行是不可逆的数据操作，按纪律先问。
- **另一个真问题**：那条座位公告里的**地点根本没被写进 `location`**（两行都是 null）——
  这才是"公告公布了地点却没更新到考试"的根因，属 **P0-5-5** 的范围（公告 → 考试改期/改地点写通）。

## 6. 红线

- 🔴 **不许给未完成的行设时间下界**（会让逾期未完成消失 = 帮用户逃避）。
- 🔴 **不许在别处再抄一份"哪几个提交态算完成"**（常量唯一来源 = `CANVAS_DONE_STATES`）。
- 🔴 **不许用 `not.in.(...)` 表达"不在已完成集合内"**：`x NOT IN (...)` 遇 NULL 求值为 NULL，
  会把所有考试/手动任务整批静默排除。
- 🔴 **不许不经确认删 `exam_dates` 行**。
