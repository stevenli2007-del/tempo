# Decisions.md — Tempo 架构决策记录（ADR）

## 这份文档是干什么的

记录 Tempo 发展过程中**影响架构、需要权衡取舍**的决策，以及**为什么这么定**。

代码会过时、文档会漂移，但"当时为什么选 A 不选 B"这件事，如果不写下来，三个月后没人记得。下次有人问"能不能换成 X"，你需要知道当初排除 X 的理由，否则要么无脑沿用，要么推倒重来。

## 什么时候该写 ADR

**该写**：

- 做了影响架构的决策（技术选型、数据模型结构、集成方式）
- 做了有明确取舍的决策（为了 A 放弃了 B）
- 「为什么不用 X」需要留痕
- 推翻或修改了之前某条 ADR

**不用写**：纯实现细节、函数怎么命名、UI 颜色这类不影响架构的选择。

## 格式规范

- 编号**单调递增，永不删除**。决策作废时把状态改成「已废弃」并注明被谁取代，保留原文。
- 每条必须包含：状态、日期、背景、决策、理由、后果、复审条件。
- 「理由」要写真实的权衡，不是给决策找借口——如果代价是什么都不写，这条 ADR 就是形式主义。

## 已接受决策

### ADR-001：产品内核是「实时检测 + 动态管理」，不是静态整理

- **状态**：已接受
- **日期**：2026-09-01

**背景**

Tempo 表层看起来的功能是：翻译 syllabus、整理课程信息、规划 study plan。但这些功能随时会被替代——任何人都能拿 GPT 解析一份 syllabus，这不是壁垒。

**决策**

产品的价值内核锚定在**实时检测 + 动态管理 + 规划**：从 Canvas / CalCentral / Google Calendar 等数据源持续更新、检测进度，并基于检测到的进度，动态规划每日任务、分解长期任务到每天。

定位一句话「课程操作系统 Course OS」保留，但价值权重要放在"实时/动态"上，而非"静态整理"。

**理由**

静态整理是一次性的、无差异的，谁都能做；而"持续接入多个数据源 + 基于变化动态调整计划"需要深度的数据接入能力和信任积累，这才是别人抄不走的东西。护城河在数据接入的深度，不在界面。

**后果**

- 功能优先级上，**同步与检测的可靠性 > 界面丰富度**。
- Phase 0 就必须验证"实时同步"这个价值点，不能等到 Phase 2 才碰。
- 任何"做一次就完事"的功能，优先级都要往后排。

**复审条件**

如果发现学生对"实时"无感、只在开学初集中使用一次——说明这个内核假设不成立，需要重新定位。

### ADR-002：Phase 0 用 Canvas Personal Access Token，接受 ToS 风险

- **状态**：已接受
- **日期**：2026-09-01

**背景**

Canvas 官方政策白纸黑字写着：*「It is a violation of Canvas API policy for a user to generate an access token to insert into an application. Applications must use approved authentication methods instead.」*

正式路径是 OAuth2 / Developer Key，但那需要伯克利机构审批，周期长、MVP 阶段等不起。

**决策**

- Phase 0 用 **Personal Access Token**，用户在设置页手动粘贴自己在 bCourses 生成的 token。
- 定性为**「验证阶段的临时手段」**，不是长期方案。
- **iCal Calendar Feed 作为 Plan B**（合规、只读、可撤销，能覆盖"作业 due date 同步"这个 Phase 0 核心需求）。
- Phase 1 必须升级为正式 OAuth，届时约谈学校 IT。

**理由**

风险性质是**平台政策（ToS）风险，不是法律责任**（见 ADR-008）。最坏后果是 Canvas 掐断接入或撤销 token，不存在法律后果。5-6 人种子用户自用、不对外分发、不公开宣传此接入方式，触发概率趋近于零。

但心态上必须区分清楚：这是"验证价值用的临时手段"，不是"产品可以长期依赖的地基"——**这个心态区分比技术怎么实现更重要**，它决定了会不会在没意识到的情况下把 PAT 写成产品的长期依赖。

**后果**

- 不能把 PAT 当作可规模化的方案宣传；规模一大，"违反 ToS"被注意到的概率跟着涨。
- Canvas 学生 token **强制过期**（2026-09-04 P0-2-1b 实测上限 **90 天**，过期时间强制必填，无 null fallback），必须做到期提醒，且提醒要基于用户实际填写的过期时间。
- 与"学校关系是战略资产"这条原则存在张力——现在不出事，但将来谈官方合作时，地基建立在"技术上被明确禁止"的方式上，谈判桌上不好看。
- token 必须 AES 加密存储，所有 Canvas 请求在服务端发起。

**复审条件**

用户规模超过约 50 人；或伯克利关闭学生自行生成 token 的入口（届时切 iCal Plan B）；或开始接触学校谈合作。

**实测确认（2026-09-01，Steven）**

登录 bCourses → Settings 确认 **"+ New Access Token" 按钮存在且可用**，PAT 路线成立。因此：

- iCal Calendar Feed **不再作为 Phase 0 的工作项**（原 P0-2-10 标记为不执行）。
- iCal 保留为**长期 Plan B**：仅在学校将来关闭学生 token 入口时启用，降级阶梯见 `Sync-Strategy.md` L3。
- 待补细节（P0-2-1b）：是否强制填写过期时间、上限天数——影响 P0-2-8 到期提醒的默认值。~~文档当前按"约 120 天、强制过期"设计，若实测不同以实测为准。~~ → ✅ **2026-09-04 已实测关闭**：过期强制必填，上限 90 天（bCourses 弹窗 "Maximum expiration is 90 days."）。P0-2-8 提醒默认值按 90 天倒推。

**关于 Phase 1 OAuth 的时机（Steven 拍板，2026-09-01）**

**不在 Phase 0 期间提前申请**，等验证结果出来后再启动。理由是申请策略与说辞应基于真实用户数据——现在空手去谈，和带着"5-6 人已验证、下学期还要用"的结论去谈，筹码完全不同。

代价已记录在 `Phase-0-MVP.md`：Phase 1 的 OAuth 可能赶不上 Fall 2026 学期。**若 Gate 0→1 评审通过，应立即启动申请，不得继续拖延。**

### ADR-003：LLM 走可插拔 provider 抽象层，默认 DeepSeek

- **状态**：已接受
- **日期**：2026-09-01

**背景**

syllabus 解析需要 LLM。Steven 倾向 DeepSeek（熟悉、成本低），但 DeepSeek 官方 API **没有多模态视觉输入**，而"扫描件/复杂排版 PDF 渲染成图再解析"这条路径需要视觉能力。

**决策**

- LLM 走一层**可插拔 provider 抽象层**，业务代码不依赖具体厂商。
- 默认 provider = **DeepSeek**。
- 若解析效果不达标，**随时可切 Claude**，只改一处配置，不动业务代码。

**理由**

沿用 Steven 在 LinkedIn AI Assistant 项目里已经验证过的 provider 抽象经验，两个项目保持一致。这样既满足"先用 DeepSeek"，又保留了切换余地——而切换到 Claude 时，多模态视觉能力顺带就有了，扫描件解析的缺口自动补上。

**后果**

- Phase 0 扫描件/复杂排版走**降级策略**：文本抽取失败就提示用户手动补充关键信息，不为此单独搭 OCR 管线，也不引入第二个 LLM。
- 抽象层本身有少量额外代码成本，但换来的是"效果不好能立刻换"的底气。

**复审条件**

解析准确率不满足需求（切 Claude 实测对比）；或需要批量处理扫描件。

### ADR-004：`exam_dates` 为可编辑权威源，tasks 中 exam 为派生缓存

- **状态**：已接受
- **日期**：2026-09-01

**背景**

"考试"这个实体同时存在于两张表：`exam_dates`（课程页结构化展示，含 exam_time / location / status 等考试特有字段）和 `tasks`（总览页合并排序，`task_type='exam'`）。两处都存，改一处不同步另一处就会出现"总览页日期和课程页日期对不上"。

**决策**

- `exam_dates` 是**可编辑的权威源**。
- `tasks` 里 `task_type='exam'` 且 `source='syllabus'` 的记录是它的**派生缓存**，由后端在 exam 创建/编辑/删除时自动同步。
- 前端**不允许直接编辑**这类 task，只允许改 `exam_dates`。
- `tasks.source_id` 对考试指向 `exam_dates.id`，用于去重与增量同步。

**理由**

两张表各自职责清晰、都不该砍：`exam_dates` 承载考试特有的字段，`tasks` 保持轻量统一以便总览页合并排序。用"派生 + 自动同步"规则消除双写，比强行合并成一张表代价小。

这也天然呼应产品的"用户可编辑、可覆盖"原则——`exam_dates` 是用户可编辑层，`tasks` 是系统视图层。

**后果**

- 后端必须实现 exam_dates 变更 → tasks 同步的逻辑，这是新增的复杂度。
- 同步逻辑本身要有失败处理（见 ADR-005 的降级要求）。

**复审条件**

如果考试与任务的字段差异消失（tasks 能完整承载考试信息），可以考虑合并。

### ADR-005：同步轮询策略——前期宽松，后期收紧

- **状态**：已接受
- **日期**：2026-09-01

**背景**

syllabus 是静态的（一学期一份），但 Canvas 是动态的：due date 会改、会延期、作业会新增。老师把 deadline 从明天改到后天，Tempo 多久能知道，直接等于产品的体验命门——如果滞后 24 小时，学生可能刚好错过一个改到明天的 deadline，而"省心"是 Tempo 的全部卖点。

**决策**

- 采用**轮询**拉取（Phase 0 无 webhook 可用）。
- **前期轮询频率宽松**，大一点可接受，先验证"实时同步是否有价值"。
- 验证通过后，再优化为更精细的增量同步与变更检测。
- 具体数值在 `Sync-Strategy.md` 定义。

**理由**

Steven 明确授权"前期轮询频率稍微大一点都 OK，后期提上来"。MVP 阶段最重要的是验证价值假设，不是优化性能——在没证明"实时同步有人要"之前，把工程精力花在精细化同步上是浪费。

**后果**

- 必须设计：失败降级（同步失败要用户可见，不能静默）、token 过期提醒、增量更新而非全量覆盖。
- 后期用户量上升时，需注意 Canvas API 限流风险。

**复审条件**

用户量上升导致 API 限流；或用户反馈"变化发现太慢"；或进入 Phase 1 后可评估更优的变更检测机制。

### ADR-006：技术栈锁定 Next.js + Supabase

- **状态**：已接受
- **日期**：2026-09-01

**背景**

个人 / 小团队开发，需要服务数量尽可能少、迭代尽可能快。

**决策**

Next.js 全栈（App Router）+ Supabase（Postgres + Auth + Storage 三合一）+ Vercel 部署。详见 `TechStack.md`。

**理由**

Supabase 一家提供数据库、认证、文件存储三件套，减少了需要接入的服务数量。免费额度足够 MVP。Next.js 全栈让前后端同仓，适合快速迭代。

**后果**

- 受 Supabase 平台限制（Edge Function 约束、免费额度上限）。
- 部署绑定 Vercel。
- 换栈成本高，所以必须用 ADR 锁死，避免开发中途反复横跳。

**复审条件**

免费额度不够；或需要 Supabase 明确不提供的能力。

### ADR-007：明确不做 CalCentral 集成与 Gradescope / Piazza 自动提交

- **状态**：已接受
- **日期**：2026-09-01

**背景**

CalCentral 集成、Gradescope 自动提交、Piazza 自动回复这类功能看起来很有价值，但它们没有官方 API，依赖模拟登录或逆向工程。

**决策**

- **不做** CalCentral 集成（学校账号认证 + 无公开 API，难度与风险都不匹配投入产出比）。
- B2 类功能（无官方 API、依赖逆向、失败后果直接影响学业）**不作为产品能力**，仅作为长期实验性、**用户主动开启（opt-in）**的功能存在。
- B2 类功能**不进主流程、不作核心卖点宣传**，且必须有清晰的失败可见性。

**理由**

维护成本高（平台一改就挂）、失败后果严重（作业没交上）、且与学校官方合作路径直接冲突。核心卖点应该始终是"理解与规划"能力（Phase 0-2），不是"替你提交"。

**后果**

Tempo 的能力边界受官方 API 限制，某些学生痛点（如 Gradescope 提交流程）暂时覆盖不到。这是有意识的取舍。

**复审条件**

相关平台官方开放 API。

### ADR-008：ToS 风险与法律风险分开定性

- **状态**：已接受
- **日期**：2026-09-01

**背景**

早期文档里笼统地使用"法律风险"来描述各种合规问题，容易把问题想得比实际严重，导致决策误判（要么过度恐慌不敢做，要么掉以轻心）。

**决策**

明确区分两类风险，文档措辞不得混用：

| 类型 | 涉及场景 | 最坏后果 |
|---|---|---|
| **平台政策（ToS）风险** | Canvas PAT 接入 | Canvas 有权终止 API 访问、撤销 token、要求停止该接入方式 |
| **法律风险** | Phase 4 past paper 资源库（版权）、FERPA 隐私数据 | 真正的法律责任 |

**理由**

两者性质与量级完全不同。Canvas PAT 场景下，每个用户看到的都是自己账号本来就能看到的数据，不涉及第三方隐私泄露，不存在法律责任；而 past paper 的版权和 FERPA 才是需要认真评估法律后果的领域。

**后果**

- 文档措辞必须精确，看到"风险"要先分清是哪一类。
- Phase 4 的 past paper 需要在启动前**单独评估版权与 FERPA**，不能等做出来再补救。

**复审条件**

进入 Phase 4 规划时。

### ADR-009：syllabus 上传走浏览器直传 Supabase Storage，不走服务端转发

- **状态**：已接受
- **日期**：2026-09-02

**背景**

`API-Contract.md` 原定上传接口为 `POST /api/v1/courses/:id/syllabus`，`multipart/form-data` 由服务端 Route Handler 转发到 Supabase Storage，单文件上限 **20MB**（`TechStack.md` 第 4 节按 Storage 免费层 1GB 额度给出）。

但文件若经 Vercel 函数转发，会撞上平台的**请求体大小上限**——而 syllabus PDF 通常在 1-5MB，把设计上限从 20MB 砍到平台能接受的值，等于为了迁就部署平台而牺牲用户侧宽裕度。

**决策**

改为**浏览器直传**（browser → Supabase Storage），服务端只负责收尾建行：

```
① 前端校验类型/大小（仅体验层，不可信）
② 前端用 session 直传私有桶，路径 {user_id}/{course_id}/{uuid}.{ext}
③ POST /api/v1/courses/:id/syllabus  { fileName, storagePath, size }
④ 服务端校验路径归属（首段 = auth.uid()）+ 文件真实存在 + 类型 + 大小
⑤ 插 syllabi 行（extract_status=pending, parse_status=pending）
```

`API-Contract.md` §3 的 multipart 契约随之改写为两步式 JSON（在 P0-1-1 交付时同步更新，不单独拆 task）。

**理由**

- **保住 20MB 设计上限**，不为平台限制牺牲用户侧宽裕度。
- **不占 Vercel 函数时长与内存**：20MB 文件过服务端会显著吃掉 Hobby 层的资源预算，而直传是浏览器与 Storage 之间的事。
- **安全边界等价**：私有桶 + `storage.objects` 的 RLS 策略按「路径首段 = `auth.uid()`」判定，与服务端的授权强度一致——不是把校验交给前端，而是把校验交给 Storage 自己的 RLS。
- 后端仍然保留**权威校验**（步骤 ④）：前端校验只是体验层，路径归属、类型、大小在服务端再查一遍。

**后果**

- **契约文档要改**：`API-Contract.md` §3 与路由总表的 multipart 描述失效，需改写为两步式。
- **多一次往返**：直传 + 建行两次请求，失败点也变成两个。
- **孤儿文件**：直传成功但建行失败，会在桶里留下无主文件。Phase 0 接受这个代价，靠 P0-3-2「一键删除账号」按用户前缀整段清理；若将来孤儿文件堆积成问题，再补一个对账清理任务。
- **前端校验不能当权威**：这条写进代码评审清单——`size` 与扩展名由客户端上报，服务端必须复核。

**🔴 未实测项（诚实标注）**

本条 ADR 的主要论据「Vercel 平台对请求体存在约 4.5MB 上限（Hobby 层）」**来自既有认知，未经本次实测**。它在决策时用于判断"20MB 走服务端转发不可行"，但不影响决策本身的另一半理由（不占函数时长、保住用户侧上限）成立。

**若该数字被证伪（即平台实际允许更大请求体），不推翻本 ADR** —— 直传在资源占用上仍更优。但应回来更新本节，避免后人依据一个未验证的数字做判断。

**复审条件**

平台请求体上限放宽且需要"上传即解析"（服务端必须摸到文件内容）；或孤儿文件清理成本失控；或将来改为需要服务端改写文件内容（如压缩、转码）。

### ADR-010：RLS 保护的资源，「越权」与「不存在」统一返回 404，不用 403

- **状态**：已接受
- **日期**：2026-09-02（P0-1-7 交付时提出，同日 Steven 拍板接受）
- **影响**：`API-Contract.md` §1.2、§1.4；所有受 RLS 保护的资源端点

**背景**

`API-Contract.md` 初版 §1.2 写的是「已登录但资源不属于当前用户 → `403`（**不返回 404**，避免通过状态码探测资源是否存在）」。

P0-1-7 实现 `app/api/v1/courses/[id]/route.ts` 时发现这条在 RLS 下**落不了地**：13 张业务表全部开着 RLS，别人的课程行在当前会话的查询里**根本不返回**。于是 `select ... eq('id', id).eq('is_archived', false).maybeSingle()` 在「不存在」和「不是你的」两种情况下拿到的是**完全一样的结果**（`data === null`, `error === null`）。服务端没有信息可以区分。

**决策**

统一返回 `404`，错误文案写成「课程不存在或无权访问」（不撒谎，也不泄漏存在性）。`403` 在 Phase 0 全项目不使用。

**理由**

要在应用层区分 403 和 404，只有一条路：用 **service role 绕过 RLS** 去探测「这行到底存不存在」。但那样做就开了一个 bypass RLS 的服务端入口，等于**主动制造了一条存在性泄漏通道**——恰好是 403-not-404 那条规则想保护的东西。为了遵守一条规则的**字面**，去破坏它的**意图**，是净损失。

所以正确的做法是：**保留意图（不泄漏存在性），换手段（用 404 实现）**。404 本身同样是"不确认存在"的语义——它只是不附带"但你没权限"这层暗示。

**后果**

- **契约文档已改**：§1.2 加偏离说明，§1.4 把 403 标为 Phase 0 不使用、404 的语义扩为「不存在或不属于当前用户」。
- **适用范围是全局的，不是 courses 个案**：syllabi / tasks / exam_dates / canvas_credentials 等所有受 RLS 保护的资源都按此执行。后续端点**不用再逐个重新论证**。
- **客户端失去了一点信息量**：前端无法区分"我输错了 id"和"我没有权限"。Phase 0 接受——这两种情况对用户的可行动作是一样的（回列表页）。
- **将来若要恢复 403**：唯一干净的办法是让 RLS 策略本身返回一个可区分的信号（如把存在性判定做成 security definer 函数且只返回布尔值、不返回行内容），而不是裸用 service role。

**复审条件**

出现真实需求要向用户区分「不存在」与「无权限」（例如将来做资源共享/协作，被拒绝的人需要知道"这个资源存在，只是没给你权限"）。

### ADR-011：PDF 文本提取用 `unpdf`，不用 `pdf-parse` 或直接引 `pdfjs-dist`

- **状态**：已接受
- **日期**：2026-09-02（生产事故复盘后，Steven 拍板）
- **影响**：`lib/extract.ts`、`next.config.mjs`、`TechStack.md` 第 2 节、`API-Contract.md` §3

**背景**

P0-1-2 上线后，`POST /api/v1/syllabi/:id/extract` 在 Vercel 上**对所有请求一律 500**，响应体为空。本地 `next start` 与端到端冒烟全绿（27/27），是典型「本地全绿、线上全红」。

上临时诊断路由抓线上错误后定位：`pdf-parse` 2.4.5 在**模块作用域**无条件执行 `new DOMMatrix()`，而 `DOMMatrix` 是浏览器 API，靠 `require('@napi-rs/canvas')`（Skia 原生二进制）补 —— canvas 加载失败时它**只 warn 不赋值**，紧接着顶层就崩。本地 macOS 装有 `@napi-rs/canvas-darwin-arm64`（23MB）所以全绿；Vercel 函数包里没有这个原生二进制。

第一次修（`pdfjs-dist` legacy 构建）**失败**，且暴露了更深的问题：`pdfjs-dist` 的现代构建**和 legacy 构建在 Vercel 上同样抛 `DOMMatrix is not defined`**。我此前「legacy 自带 polyfill」的判断是错的 —— 本地能看到 `DOMMatrix` 其实还是 canvas 提供的，**本地测试环境被同一个「只存在于本地的依赖」污染了**，跟 `pdf-parse` 是同一个陷阱。

**决策**

PDF 提取用 `unpdf` 1.8.1；`pdfjs-dist` 保留在依赖里，但**只当数据包用**（提供 `standard_fonts/` 与 `cmaps/`，不 import 它的 JS）。

**理由**

- unpdf 的存在意义就是解决这个坑：它用 rolldown 重新打包 pdfjs，**字符串替换剥掉浏览器 API 引用、worker 内联、补缺失的全局对象**，产出单文件、**零运行时依赖**、不需要任何原生二进制。
- 备选方案都不划算：① 打包 `@napi-rs/canvas` 进函数包 → +23MB、冷启动变慢、AL2023 上还有二次翻车风险；② 自写 `DOMMatrix` stub → 赌 pdfjs 内部「只构造不调用」矩阵方法，版本升级即碎。
- 「文件都在、import 就崩」这个失败模式**响应体为空**，只能靠临时诊断路由抓，排查成本高，值得一次性根治。

**后果**

- `serverExternalPackages: ['unpdf']`（它是预打包产物，没必要让 Turbopack 再过一遍手）；`outputFileTracingIncludes` 显式打进 `pdfjs-dist` 的 `standard_fonts/**` 与 `cmaps/**` —— 这两个目录是运行时按路径读的，不在 import 图里，不声明就不会进函数包。
- 释放文档用 `pdf.cleanup()`（pdf.js v5 把 `destroy()` 改名了）。
- **给未来留的方法论**：验证「依赖里含原生二进制 / 浏览器 API」的库时，本地必须 `delete globalThis.DOMMatrix` 再 import，否则本地残留的 canvas 会让人得出「换库已修好」的错误结论 —— 这次就因此白推了一次部署。

**复审条件**

unpdf 停止维护，或出现官方 serverless 构建（pdfjs 官方原生支持 Node 且不再依赖 canvas）。

### ADR-012：`/parse` 同步返回 200，并按 DB 实际约束收敛契约

- **状态**：已接受
- **日期**：2026-09-03

**背景**

`API-Contract.md` §3 把 `POST /syllabi/:id/parse` 定义成 **202 异步 + 前端 1.5 秒轮询 `/parse-status`**，
§4 又要求保存时「更新 `llm_run_id` 归因」。动手时发现三处与 DB 现实对不上：

1. **没有板块级进度的存储落点**。`llm_runs` 只有 `purpose` / `status` 两列，没有板块维度；
   `syllabi` 也只有单个 `parse_status`。要做板块级进度就必须加字段走迁移。
2. **Vercel 上响应返回后 pending promise 会被冻结**，异步要靠 Next 的 `after()` 兜底，
   多一层失败模式。
3. **五张板块表都没有 `llm_run_id` 列**（只有 `parse_corrections` 有），§4 的第 2 条无法按字面实现。
4. `syllabi.parse_status` 的 CHECK 约束是 `pending / processing / completed / failed`，
   **没有**契约里写的 `partial`。

**决策**

- **`/parse` 与 `/reparse` 同步返回 200**，跑完 LLM 直接落库并返回结果。`GET /parse-status`
  **本阶段不实现**（归 P0-1-11，同步模式下没有"进行中"这个中间态可查）。
- **部分失败不是 HTTP 错误**：五个板块全失败才写 `parse_status = 'failed'`；部分失败写
  `'completed'` + `parse_error` 写明失败了几块是哪几块，成功的部分照常落库并返回。
- **`llm_run_id` 归因只落在 `parse_corrections` 上**（P0-1-5b），五张板块表不加这一列。
- **重解析的覆盖规则**：只删 `source = 'syllabus'` 的行，`source = 'manual'` 与
  `is_confirmed = true` 的行保留（`grade_components` / `exam_dates` 两表有 `is_confirmed` 标记）。

**理由**

- 实测五板块**并发只要 3.2 秒**。为 3.2 秒引入「进度存储 + 后台执行兜底 + 状态机」这一整套，
  复杂度与收益严重不成比例 —— 而且轮询的复杂度最终会漏到前端。
- 板块级进度真正的价值在「长 syllabus 让用户等得住」。真到那一步（syllabus 普遍 >3 万字符、
  或要做分块合并时）再上异步，那时连分块进度的存储需求都会更清楚。
- 归因用在哪儿？ADR-003 的复审条件是「按 provider / 模型 / prompt 版本对比准确率」，
  而准确率的数据源是**用户修正**（`parse_corrections`）—— 那张表本来就有 `llm_run_id`。
  给五张板块表各加一列，换不来额外的分析能力，只多五个列和一次迁移。
- 覆盖规则的理由与 ADR-004 同源：**用户确认过的内容是权威**。宁可重新解析时不刷新它，
  也不能把用户的确认冲掉 —— 冲掉是不可逆的，不刷新只是少一次机会。

**后果**

- 前端从「发请求 → 轮询 → 拿结果」简化成「发请求 → 拿结果」，但**等待期间要有 loading 态**，
  实测 3 秒的等待不做反馈会让用户以为卡了。
- 同步调用占满 Vercel 函数时长：`maxDuration = 60`，实测远够用。
- **已知留白**：五张表的写入**没有跨表事务**（supabase-js 不支持多语句事务，除非写 RPC）。
  逐表「先删后插」，中途失败会留下部分写入状态；失败会抛 500 且 `parse_status` 不会被写成
  completed，用户重试一次即可自愈。要做原子就加一个 Postgres 函数包住五张表的写操作。
- 若 P0-1-11 要做进度可视化，本 ADR 需复审（那是唯一会推翻同步选择的场景）。

### ADR-013：不逆向第三方平台，只走官方授权接口

- **状态**：已接受
- **日期**：2026-09-13（Steven 提出「为什么 Gradescope 交了作业 Tempo 还显示待完成」后拍板）
- **影响**：`Roadmap.md` §10 明确不做、`Phase-0-MVP.md` P0-3-10、所有"接入某平台"类需求的前置判断

**背景**

Chem 1A 的作业提交在 Gradescope，Canvas 侧只有一个 LTI 外链。学生交了作业，Canvas（因而 Tempo）仍显示"待完成"——Steven 问能不能直接接 Gradescope。

查证结论：

- **Gradescope 官方明确表示没有 public API**（其帮助中心原话：*we don't have a public API… track this feature request*）。它与 Canvas 的集成**只走 LTI 1.3 / LTI Advantage 的成绩回传（AGS）**，没有面向学生的 REST 接口。
- 存在的只有**社区逆向库**（如 `nyuoss/gradescope-api`，用 email + password 登录打私有端点）。
- Data C8 这类课程自建网站（`data8.org/fa26`）同样没有任何接口。

**决策**

**不逆向、不模拟登录、不索取用户在第三方平台的密码。** 一个平台只有三种接入姿态：

| 姿态 | 适用 | 例子 |
|---|---|---|
| ① 官方接口直连 | 有官方授权接口 | Canvas REST API、Google Calendar / Gmail OAuth |
| ② 间接获取 | 无接口但会发邮件 | Gradescope、Piazza、各类课程通知（见 ADR-014） |
| ③ 用户提供 | 以上皆无 | Data C8 课程网站 → 截图 / 粘贴 / 对话补充 |

**理由**

任一条都足以否决逆向：① 要索取用户**最敏感**的密码（比 Canvas PAT 敏感一个量级，且往往是学校统一身份密码）；② 违反平台 ToS；③ 私有端点无契约，随时变，库随时废，维护成本永续；④ 失败后果直接落在学业上（交作业），而失败可见性还极差。

性质上属于总蓝图 Phase 3 的 **B2 类（高风险、opt-in、不作卖点）**，本 ADR 是 **ADR-007 的延伸**（ADR-007 只覆盖了"不做自动提交"，未覆盖"不做数据读取"）。

**后果**

- Tempo **不可能**做到"所有平台全自动"——这是能力边界，不是待办事项。产品必须诚实呈现边界（见 ADR-015 与「待确认」态）。
- 「用户什么都不用做」的愿景，只能靠**选对入口**（官方接口 + 邮件）实现，不能靠爬。
- 对无接口平台，**降低确认成本**是唯一正解：一键确认 / 截图识别（P0-3-9）/ 邮件解析（ADR-014）。

**复审条件**

相关平台开放官方 API；或出现官方认可的 LTI Advantage 深度集成路径。

### ADR-014：邮件是覆盖「无接口平台」的通用适配器

- **状态**：已接受
- **日期**：2026-09-13
- **影响**：`Phase-0-MVP.md` P0-3-11（邮件通道）、Phase 1 的 Google OAuth 范围

**背景**

无官方接口的平台（Gradescope、Piazza、课程通知、lab 取消通知）有一个共同点：**它们都会给用户发邮件**。逐平台接入是一条死路，但"抓住邮箱"能一次性接上所有平台——**完全不用碰 Gradescope**。

**决策**

**邮件是覆盖长尾平台的主通道**，两条路径按成本排序：

| 路径 | 自动化程度 | 成本 | 时机 |
|---|---|---|---|
| ① **转发到 Tempo 专属地址** | 半自动（用户转一次） | 低：只需入站邮件解析，**零 OAuth、零安全评估** | **M3 可做（P0-3-11）** |
| ② **Gmail API**（OAuth 只读） | 接近全自动（可订阅推送） | 高：Gmail 只读属 Google **restricted scope**，需安全评估，周期以月计，还需隐私政策 | Phase 1 |

先用 ① 打通闭环以验证"邮件能自动更新 task 结构"这个假设，② 留到 Phase 1 与 Google Calendar 一起做。

**理由**

① 的成本比 ② 低一个数量级，却能在**几天内**验证同一个假设；② 卡在 Google 的安全评估上，周期不可控，不该成为验证的前置依赖。这也是「内核不能跳级」的反面应用——**验证假设要挑最短路径**。

**后果**

- 需要入站邮件解析基础设施（收信 → 识别来源 → 抽事件 → 落库 / 改 task）。
- **截图档（P0-3-9）从"主路"降级为"兜底"**：能自动拿到的走邮件，拿不到的才让用户随手丢一张图。
- 邮件内容同样含个人信息，隐私说明（A12）与删账号级联清单要覆盖邮件正文的存储。

**复审条件**

Phase 1 接入 Google OAuth 时重新评估 ②；或入站邮件解析准确率不足时。

### ADR-019：邮件入站用「密址绑定 + 纯入站」，砍「注册邮箱绑定」与「就绪回信」

- **状态**：已接受
- **日期**：2026-09-17（P0-3-11 落地时）
- **影响**：`Phase-0-MVP.md` P0-3-11（入站-only）、`lib/email/*`、`app/api/v1/email/*`、`workers/inbound-email/*`

**背景**

P0-3-11 把 ADR-014 的「转发到 Tempo 专属地址」落地。开工前与 Steven 拍板两个边界：

1. **绑定方式**：用「每用户密址」`inbound+<token>@<域>` 识别用户，**不**用「注册邮箱 From 头」识别。
2. **范围**：只做**入站**（转发 → 解析 → 只写 `status='done'`），**出站推送整体归 P0-3-14**；因此**不做**「地址已就绪」验证回信（那属于出站）。

**决策**

1. **密址绑定，不用 From 绑定**：token 即身份，构造上不可伪造（行业标配）。`From` 头可伪造，要安全用发件人识别必须额外校验 SPF/DKIM/DMARC，复杂度与收益不成正比 —— 故只用 token。
2. **纯入站**：Worker 只把邮件 POST 给 Vercel 路由；所有解析 / 匹配 / 落写都在 Next 应用内（复用 `lib/tasks/match.ts` 确定性匹配 + `PATCH status`）。不发任何出站邮件。
3. **只写 `status='done'`**：邮件识别出「已提交」时，确定性匹配到现有任务即标记完成；**绝不自动新建任务**、**绝不自动改 dueDate**（那会与 Canvas 同步打架、且属出站/提醒范畴）。其余事件（改期 / 新作业）只入审计日志 `email_inbound_events`，不落写。
4. **红线**：邮件只经 `PATCH status`，**绝不写 `submission_state` / `submitted_at`**（ADR-015，那两列仅 Canvas 同步可写）。

**理由**

密址绑定把「跨账户注入」风险从「需校 SPF/DKIM/DMARC」降到「构造上不可能」；纯入站把 3-11 与 3-14 的边界一刀切开，避免两卡重复造出站逻辑。

**复审条件**

P0-3-14 落地后重新评估「改期 / 新作业」是否要升级为落写；或出站推送需要复用入站地址时，再决定是否补回信能力。

**否决的替代方案：连用户收件箱（inbox-pull / IMAP / Gmail API OAuth）（2026-09-17）**

- **提议**：把邮件 ingestion 从「密址推送」改为「Tempo 连用户真实收件箱（OAuth），读全部邮件、按发件人/LLM 分类」，用户只需授权一次、零逐平台配置。
- **否决理由**：
  1. **主流路径已被 Canvas 同步白嫖**：当 Gradescope 是 Canvas 的 submission type（external tool）时，Gradescope 经 LTI grade passback 把 `submission_state` 写回 Canvas，Tempo 的 Canvas 同步直接拿到 `submitted` —— 此场景下邮件**冗余**，连收件箱纯属额外成本。
  2. **邮件通道只在「Canvas 盲区」才必需**：(a) Canvas 作业为 `on_paper` / `no_submission`（`submission_state=null`，ADR-015 显「待确认」）；(b) 完全在 Canvas 外的平台（PrairieLearn / 独立门户 / 教授直邮）。为覆盖这小撮去读整个收件箱（隐私面 + 存邮箱凭据 + 轮询/PubSub 频率成本）对 MVP 是 **overkill**。
  3. 成绩回执（graded+分数）价值低：Tempo 是规划 OS，不追分，`submission_state` 到 `submitted` 已够。
- **结论**：**不推翻本 ADR、不建 inbox-pull**。保留密址转发（`inbound+<token>@`）作为「Canvas-blind / 非 Canvas 作业」的**手动兜底**（用户手转或把该平台通知邮箱指向密址）。隐私面、凭据存储、频率成本全免。
- **触发重议的条件**：真实用户数据表明其课程大量是 `on_paper`/非 Canvas 接法、密址手动兜底摩擦过大时，再评估 inbox-pull。

### ADR-015：`submission_state` 与 `status` 分列，同步只写前者

- **状态**：已接受
- **日期**：2026-09-13
- **影响**：`Database.md` §3.9 / §4.1、`API-Contract.md` §5、`Phase-0-MVP.md` P0-3-10

**背景**

Steven 报 #7：R4A 的 I.4 讨论作业**已经交了**（Canvas 显示 Not Yet Graded），Tempo 仍显示"待完成"。根因不是解析问题——`lib/canvas/assignments.ts` 拉作业**根本没要 submission**（`include[]=submission` 缺失），所以 `tasks.status` 目前**只由用户手勾**驱动。

要补上 Canvas 的提交状态，同时**不能**破坏 10.1 第 13 条那条既有铁律（「写入字段封闭集合绝不含用户可改字段」）。

**决策**

- 新增 `tasks.submission_state`（Canvas 侧真相，**同步可写**）与 `tasks.submitted_at`。
- `tasks.status`（用户主权）**语义不变，同步永不写**。
- 展示层做**合并**，不做双向写。

**理由**

把"外部真相"和"用户判断"分成两个字段，从根上消除"同步与手勾互相打架"这类最难查的 bug——这类 bug 昂贵在于它**间歇出现、无法复现**。代价只是展示层多一个合并函数，远低于事后排查成本。

**映射与展示规则**

| Canvas 侧情形 | `submission_state` | UI 展示 |
|---|---|---|
| `graded` / `submitted` / `pending_review` | 同名值 | 已完成区（标「已提交（Canvas）」） |
| `unsubmitted` + `missing`（非外链） | `missing` | 逾期未交（区别于"逾期未完成"） |
| **`external_tool`（Gradescope 等 LTI）的"未交"信号或完全无记录** | `external_unconfirmed` | **待确认（外部平台提交）** 🔴 不得显示"待完成" |
| `none` / `not_graded` / `on_paper`（考勤、纸质） | `null` | 保留手勾（Canvas 无完成态概念） |

> 🔴 **外链类信号分方向**（2026-09-13 实测补强）：LTI 回传的**正信号**采信；Canvas 自己推断的**负信号**降级为「待确认」——
> 它看不见 Gradescope 里的提交，实测出现过"已在 Gradescope 交、Canvas 仍报 `unsubmitted`"，直接渲染"未完成"就是诬告（ADR-013）。

**两个方向的不对称规则（刻意）**

- 用户手勾的 `done` **永不回退**（延续 P0-2-5 的验证结论）。
- Canvas 自身状态**允许回退**（老师撤回 / 重设时照搬真相）。

**理由**：手勾是用户的最高裁决，回退等于否定用户；Canvas 状态是事实，不照搬就是撒谎。写成同一条规则必然错一边。

**`isOverdue` 连带修正**：已提交的逾期任务**不得再标红**（他明明交了）。判定改为「过了 due **且** 两个来源都没完成」。

**后果**

- 一次迁移（加两列）+ 一次回归（与日期时区修复同一片代码，见 P0-3-10）。
- 🔴 **主动偏离内核阶梯**：`Roadmap.md` §3 Phase 0 列的「有 deadline，无完成状态」改为「有提交状态」。正当性——内核阶梯禁的是**跳级到规划**（在脏输入上做 Phase 2 的智能）；**同步准确性不是跳级**，且"任务状态对不对"直接决定用户是否信任 Tempo。

**复审条件**

引入多数据源冲突识别（Phase 1）时，需定义"Canvas 真相 vs 用户手勾 vs 邮件解析"三者的仲裁顺序。

### ADR-016：hands-off 优先——优化「用户操作量」，不是「使用频率」

- **状态**：已接受
- **日期**：2026-09-13（Steven：「我想做的是一个非常非常智能化、hands-off 的梳理规划平台」）
- **影响**：`PRD.md` §8.1 指标、`Roadmap.md` G0-7、所有交互设计决策、`CodingRules.md` §10.1 第 17 条

**背景**

`PRD.md` §8.1 的「7 日回访次数 ≥ 3 次/人」与 `Roadmap.md` G0-7 把"用户来得勤"当正向指标。这与产品北极星冲突：**Tempo 的卖点是减少用户打开 Canvas 的次数**，如果用户必须频繁回到 Tempo 才能拿到信息，那只是把成本从 Canvas 搬到了 Tempo——这是 Steven 明确担心的一点。

**决策**

**用户操作量趋近于 0 才是成功。** 六条设计规则：

| # | 规则 |
|---|---|
| R1 | **默认零操作** —— 任何"需要用户点一下"的设计，先问"这能不能自动？" |
| R2 | **有操作也必须是"顺手"，不是"必须"** —— 一键确认、随手截图，单次 ≤3 秒 |
| R3 | **不确定就标「待确认」，绝不猜** —— 猜错会让用户被迫回来纠正，那是最贵的操作 |
| R4 | **Tempo 找人，不是人找 Tempo** —— 主动推送 > 被动等待打开 |
| R5 | **不做惩罚性激励**（streak / 断签）—— 作业 deadline 已有真实惩罚，再加惩罚只会制造焦虑 |
| R6 | **每个新功能都要过一遍**：这增加了还是减少了用户的操作量？ |

**指标口径随之改造**

| 指标 | 语义 | 方向 |
|---|---|---|
| 打开 Canvas 次数 | 核心卖点（G0-4 已在测） | **越低越好** |
| **人工干预率**（用户手动补录/修正 ÷ 自动获取事件） | **hands-off 的核心 KPI**（新增） | **越低越好** |
| 主动查看次数 | 留存信号 | 保持即可，**不代表价值** |
| 被动核对次数（"不放心的回来看看有没有漏"） | 信任缺口 | **越低越好，趋近于 0** |

**理由**

"用户来得勤"在 hands-off 哲学下是**反指标**：需要频繁回来，说明他不信任 Tempo 已经替他看住了。同理，Duolingo 式的 streak 惩罚建立在"每天 5 分钟、失败无代价"上，而**作业交不上就扣分**——给已有真实惩罚的体系再加惩罚，学业压力大的学生会第一个卸载。

**后果**

- 架构方向从「拉」变「推」：当前同步触发器是"用户打开 dashboard"（T1），用户不来数据就不新，**结构性矛盾**。需补① 入站（邮件/外部事件）② 出站（主动摘要提醒）。
- 越 hands-off 越需要**诚实 + 可审计**：高精度或显式标注不确定（R3）、提供"我做了什么"的轻量日志（不要求操作）、关键事项宁可多提醒一次。
- 🔴 **顺序纪律**：数据准确 → 可视化 → 激励。在完成状态还是错的（#7）时做进度条与庆祝动画，**等于庆祝一件没发生的事**，信任一次就崩。

**复审条件**

出现"用户完全不打开、但仍完成任务"的形态（说明 hands-off 真正成立）；或有数据表明用户需要更多主动触达。

### ADR-017：产品定位是「每个人的电子秘书（Jarvis）」，不是又一个日历 App

- **状态**：已接受
- **日期**：2026-09-13（Steven：「我不想做一个 calendar app，我想做一个类似每个人都能有的私人秘书」）
- **影响**：`Roadmap.md`、`PRD.md`、所有交互与功能取舍；本 ADR 是 [ADR-001](./Decisions.md#adr-001) / [ADR-016](./Decisions.md#adr-016) 的**定位层收口**

**背景**

M3 打磨到一半，Steven 提出一个尖锐的自我怀疑：**「为什么我觉得我们越做越像 Google Calendar？」**

这个怀疑有事实依据：Canvas 已能把手上的任务实时同步进 Google Calendar，而 Tempo 的表层产出
（任务列表、截止日、日历视图）**截图上看确实像一个 todo / 日历**。如果 Tempo 只是"又一个显示
deadline 的地方"，那它没有存在理由 —— 用户已经在 Canvas 和 GCal 里看到了。

**决策**

把产品身份**写死**为：**每个人都能拥有的「钢铁侠的 Jarvis」—— 一个电子私人秘书。**

判据（每个新功能都要过这一关）：

> 这个功能是让平台**更懂用户、更能替他行动**，还是只是**多一种显示方式**？
> 若只是"显示"，而 Google Calendar 也能显示 —— **不做**。

**日历 vs 秘书（这条区分是本节的核心）**

| | 日历（含 Canvas→GCal） | 秘书（Tempo） |
|---|---|---|
| 本质 | **输出面**：你往里放、你往外看 | **流水线**：输入 → 理解 → 行动 |
| 接入 | 哑管道，镜像**一个**源 | 合并**多**源（syllabus / Canvas / 邮件 / 对话 / 截图）并解决冲突 |
| 智能 | 无 —— 原样搬 | 读懂（M1 解析）/ 判态（M2 提交态）/ 对齐权威源（`exam_dates`）/ 匹配消歧（3-8b） |
| 主动性 | 从不主动 | **主动**（Tempo 找人，不是人找 Tempo，ADR-016 R4） |

Canvas→GCal **做不到**的：合并 6 份 syllabus + Canvas + 用户随口说 + 邮件；去重；判断哪个真的急；
听懂自然语言；回答"你现在该干什么"。

**理由**

- 现有资产已经证明了 Tempo 在"秘书"一侧：**M1** 把 PDF 读懂成结构、**M2** 判断"交没交"而非
  "截止几号"、`exam_dates` 作为权威源自动带动派生任务、**3-8 / 3-8b** 听懂人话去查改本子 ——
  这些 Google Calendar 一件都做不到。
- 会"像日历"，是因为截图只拍得到**输出面**；真正的差异在**流水线**里，拍不出来。所以真正的风险不是
  "在做日历"，而是"让人一眼看出**我们不是**日历的那部分还没建全"。
- 与 [ADR-001](./Decisions.md#adr-001)（价值在"实时/动态"，护城河在数据接入深度）、
  [ADR-016](./Decisions.md#adr-016)（hands-off：用户操作量趋近 0 才是成功）同根。

**后果**

- 🔴 **不做"日历 App"的功能**：月视图、拖拽改期、时间段、重复事件 —— 这些是"日历"的陷阱。
- 🔵 **优先做"秘书"的功能**：**主动**（主动提醒 / 优先级建议）、**摄入广度**（截图 3-9 / 邮件 3-11 /
  对话 3-8）、**理解**（匹配 / 冲突 / 去重）。
- 衡量"像不像秘书"的正指标是 ADR-016 那套：**打开 Canvas 次数**、**人工干预率**、**被动核对次数**，
  全都越低越好 —— 而**不是**"打开 Tempo 的次数"。
- ⚠️ **已知缺口**：「主动提醒 / 优先级建议」目前**没有对应卡**（M3 未排）—— 按本 ADR 的口径，它是
  "秘书"最核心的护城河能力，应尽快立项，而不是等 3-12 扫尾之后。

**复审条件**

出现"用户完全不打开 Tempo、但事情仍被安排好"的形态（说明秘书真正成立）；或数据表明用户其实是拿
Tempo 当纯日历用（说明定位错位，需重新审视）。

### ADR-018：LLM provider 按**能力**路由（文本 DeepSeek / 视觉 Qwen 通义千问，中国）

- **状态**：已接受
- **日期**：2026-09-13（P0-3-9 领卡时，关闭待决项 **O-11**）
- **影响**：`lib/llm/*`（`types.ts` / `env.ts` / `index.ts` / `run.ts` / 新增 `providers/claude.ts` 与 `providers/qwen.ts`）、`TechStack.md` §2 / §5.2、`API-Contract.md` §5、`Phase-0-MVP.md` P0-3-9
- **关系**：本条是 [ADR-003](./Decisions.md#adr-003)（可插拔 provider 抽象层）的**能力维度扩展**，不推翻它

**背景**

ADR-003 立了 provider 抽象层，承诺「切换只改配置、业务代码不动」。但落地时 `LLM_PROVIDER` 是**单一全局开关** —— 语义是"全站换一家"。

P0-3-9（对话框·截图档）需要**视觉**，而 DeepSeek 无视觉（ADR-003 已知）。于是"换一家"与"只让图片走另一家"正面冲突：

- 走**全局切 Claude**：每次 syllabus 解析（五板块）也搬到 Claude —— 成本上升，且 **P0-3-4 刚修好的解析质量必须重跑回归自证不退**，等于让一个低风险的图片功能去刺激高风险文本链路。
- 走**图片路径绕过抽象层**：在抽象层旁边开一条影子通道，ADR-003 的可插拔承诺当场作废（下次换视觉厂商就要改业务代码）。

**决策**

1. provider 选择**按能力**而非全局：`capability ∈ { text, vision }`。
   - `text` → 环境变量 `LLM_PROVIDER`（默认 `deepseek`），模型 `LLM_MODEL`（默认 `deepseek-chat`）
   - `vision` → 环境变量 `LLM_PROVIDER_VISION`（默认 `qwen`），模型 `LLM_MODEL_VISION`（默认 `qwen-vl-plus-latest`，中国区 DashScope）；需切回 Claude 时设 `LLM_PROVIDER_VISION=claude` + `ANTHROPIC_API_KEY`
2. `LLMMessage.content` 从 `string` 扩为 `string | LLMContentPart[]`：`{ type:'text', text }` / `{ type:'image', mediaType, dataBase64 }`。**每个 adapter 自己映射到厂商格式**，业务代码只构造这两种块。
3. `LLMProvider` 增加**能力声明**；`getLLMProvider(capability)` 在「选中的 provider 不支持该能力」时**立刻抛 `LLMConfigError`**（fail closed）—— 不允许一个无视觉的 provider 静默接到图片请求、然后返回一个看起来很像"没识别出任务"的空结果。
4. 新增 `claude` / `qwen` adapter，均用**原生 fetch**（与 `deepseek.ts` 同构，**零新依赖**，不引官方 SDK）。`qwen` 走 DashScope 的 OpenAI 兼容端点，图片块映射为 `image_url` 的 `data:` URL。
5. **只加环境变量，不加表结构**。`llm_runs.provider` 从此会出现 `claude` / `qwen` 行 —— 这正是 ADR-003 复审条件所需的数据。

**理由**

保住 ADR-003 的原意（业务代码不碰厂商），**同时不必为视觉把全站搬到贵的那家**。文本抽取是**高频 + 量大**（每次解析五板块），图片是**低频 + 少量**；让高频留在便宜的那家，是唯一划算的排布。这也是"能力路由"而非"全局切换"的全部论点 —— 不是因为多 provider 更时髦，而是因为**两类负载的成本结构差一个数量级**。

**后果**

- 配置项从 1 个变 2 个，**环境变量错配的失败模式多了一种** → 必须 fail closed，且报错文案要**指名缺哪个变量**（沿用 `lib/llm/env.ts` 既有风格）。
- ⚠️ **统计陷阱（重要）**：`llm_runs` 的 `provider` 维度从此**不再单调**。按 provider 比准确率时必须**同时带上 capability** —— 否则"Claude 准确率更低"这个结论可能只是因为它只处理了更难的那部分输入（截图）。ADR-003 的复审条件（按 provider / 模型 / prompt 版本对比准确率）从此要按 `(capability, provider, model)` 三元组切分。
- 新增 provider = 写一个 adapter + 声明能力；**不新增能力时零成本**（老调用方一行不改）。
- 隐私面：截图走通义千问 Qwen（阿里云中国区 DashScope），与 DeepSeek（中国境内）**同在中国**，无数据出境 → 待决项 **O-08** 已解决（见 P0-3-9 执行卡与 `Security-Privacy.md` 第 6 节）。

**复审条件**

出现第三种能力（audio / 长文档批处理）；或**图片量超过文本量**（那时正解是给 vision 也换一个便宜 provider，而不是退回全局切换）。
