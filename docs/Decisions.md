# Decisions.md — Tempo 架构决策记录（ADR）

## 这份文档是干什么的

记录 Tempo 发展过程中**影响架构、需要权衡取舍**的决策，以及**为什么这么定**。

代码会过时、文档会漂移，但"当时为什么选 A 不选 B"这件事，如果不写下来，三个月后没人记得。下次有人问"能不能换成 X"，你需要知道当初排除 X 的理由，否则要么无脑沿用，要么推倒重来。

## 什么时候该写 ADR

**该写**：

- 做了影响架构的决策（技术选型、数据模型结构、集成方式）
- 做了有明确取舍的决策（为了 A 放弃了 B）
- 「为什么不用 X」需要留痕
- 推翻或修改了之前某条 ADR

**不用写**：纯实现细节、函数怎么命名、UI 颜色这类不影响架构的选择。

## 格式规范

- 编号**单调递增，永不删除**。决策作废时把状态改成「已废弃」并注明被谁取代，保留原文。
- 每条必须包含：状态、日期、背景、决策、理由、后果、复审条件。
- 「理由」要写真实的权衡，不是给决策找借口——如果代价是什么都不写，这条 ADR 就是形式主义。

## 已接受决策

### ADR-001：产品内核是「实时检测 + 动态管理」，不是静态整理

- **状态**：已接受
- **日期**：2026-09-01

**背景**

Tempo 表层看起来的功能是：翻译 syllabus、整理课程信息、规划 study plan。但这些功能随时会被替代——任何人都能拿 GPT 解析一份 syllabus，这不是壁垒。

**决策**

产品的价值内核锚定在**实时检测 + 动态管理 + 规划**：从 Canvas / CalCentral / Google Calendar 等数据源持续更新、检测进度，并基于检测到的进度，动态规划每日任务、分解长期任务到每天。

定位一句话「课程操作系统 Course OS」保留，但价值权重要放在"实时/动态"上，而非"静态整理"。

**理由**

静态整理是一次性的、无差异的，谁都能做；而"持续接入多个数据源 + 基于变化动态调整计划"需要深度的数据接入能力和信任积累，这才是别人抄不走的东西。护城河在数据接入的深度，不在界面。

**后果**

- 功能优先级上，**同步与检测的可靠性 > 界面丰富度**。
- Phase 0 就必须验证"实时同步"这个价值点，不能等到 Phase 2 才碰。
- 任何"做一次就完事"的功能，优先级都要往后排。

**复审条件**

如果发现学生对"实时"无感、只在开学初集中使用一次——说明这个内核假设不成立，需要重新定位。

### ADR-002：Phase 0 用 Canvas Personal Access Token，接受 ToS 风险

- **状态**：已接受
- **日期**：2026-09-01

**背景**

Canvas 官方政策白纸黑字写着：*「It is a violation of Canvas API policy for a user to generate an access token to insert into an application. Applications must use approved authentication methods instead.」*

正式路径是 OAuth2 / Developer Key，但那需要伯克利机构审批，周期长、MVP 阶段等不起。

**决策**

- Phase 0 用 **Personal Access Token**，用户在设置页手动粘贴自己在 bCourses 生成的 token。
- 定性为**「验证阶段的临时手段」**，不是长期方案。
- **iCal Calendar Feed 作为 Plan B**（合规、只读、可撤销，能覆盖"作业 due date 同步"这个 Phase 0 核心需求）。
- Phase 1 必须升级为正式 OAuth，届时约谈学校 IT。

**理由**

风险性质是**平台政策（ToS）风险，不是法律责任**（见 ADR-008）。最坏后果是 Canvas 掐断接入或撤销 token，不存在法律后果。5-6 人种子用户自用、不对外分发、不公开宣传此接入方式，触发概率趋近于零。

但心态上必须区分清楚：这是"验证价值用的临时手段"，不是"产品可以长期依赖的地基"——**这个心态区分比技术怎么实现更重要**，它决定了会不会在没意识到的情况下把 PAT 写成产品的长期依赖。

**后果**

- 不能把 PAT 当作可规模化的方案宣传；规模一大，"违反 ToS"被注意到的概率跟着涨。
- Canvas 学生 token **强制过期**（当前上限约 120 天，非早期文档的 90 天），必须做到期提醒，且提醒要基于用户实际填写的过期时间。
- 与"学校关系是战略资产"这条原则存在张力——现在不出事，但将来谈官方合作时，地基建立在"技术上被明确禁止"的方式上，谈判桌上不好看。
- token 必须 AES 加密存储，所有 Canvas 请求在服务端发起。

**复审条件**

用户规模超过约 50 人；或伯克利关闭学生自行生成 token 的入口（届时切 iCal Plan B）；或开始接触学校谈合作。

**实测确认（2026-09-01，Steven）**

登录 bCourses → Settings 确认 **"+ New Access Token" 按钮存在且可用**，PAT 路线成立。因此：

- iCal Calendar Feed **不再作为 Phase 0 的工作项**（原 P0-2-10 标记为不执行）。
- iCal 保留为**长期 Plan B**：仅在学校将来关闭学生 token 入口时启用，降级阶梯见 `Sync-Strategy.md` L3。
- 待补细节（P0-2-1b）：是否强制填写过期时间、上限天数——影响 P0-2-8 到期提醒的默认值。文档当前按"约 120 天、强制过期"设计，若实测不同以实测为准。

**关于 Phase 1 OAuth 的时机（Steven 拍板，2026-09-01）**

**不在 Phase 0 期间提前申请**，等验证结果出来后再启动。理由是申请策略与说辞应基于真实用户数据——现在空手去谈，和带着"5-6 人已验证、下学期还要用"的结论去谈，筹码完全不同。

代价已记录在 `Phase-0-MVP.md`：Phase 1 的 OAuth 可能赶不上 Fall 2026 学期。**若 Gate 0→1 评审通过，应立即启动申请，不得继续拖延。**

### ADR-003：LLM 走可插拔 provider 抽象层，默认 DeepSeek

- **状态**：已接受
- **日期**：2026-09-01

**背景**

syllabus 解析需要 LLM。Steven 倾向 DeepSeek（熟悉、成本低），但 DeepSeek 官方 API **没有多模态视觉输入**，而"扫描件/复杂排版 PDF 渲染成图再解析"这条路径需要视觉能力。

**决策**

- LLM 走一层**可插拔 provider 抽象层**，业务代码不依赖具体厂商。
- 默认 provider = **DeepSeek**。
- 若解析效果不达标，**随时可切 Claude**，只改一处配置，不动业务代码。

**理由**

沿用 Steven 在 LinkedIn AI Assistant 项目里已经验证过的 provider 抽象经验，两个项目保持一致。这样既满足"先用 DeepSeek"，又保留了切换余地——而切换到 Claude 时，多模态视觉能力顺带就有了，扫描件解析的缺口自动补上。

**后果**

- Phase 0 扫描件/复杂排版走**降级策略**：文本抽取失败就提示用户手动补充关键信息，不为此单独搭 OCR 管线，也不引入第二个 LLM。
- 抽象层本身有少量额外代码成本，但换来的是"效果不好能立刻换"的底气。

**复审条件**

解析准确率不满足需求（切 Claude 实测对比）；或需要批量处理扫描件。

### ADR-004：`exam_dates` 为可编辑权威源，tasks 中 exam 为派生缓存

- **状态**：已接受
- **日期**：2026-09-01

**背景**

"考试"这个实体同时存在于两张表：`exam_dates`（课程页结构化展示，含 exam_time / location / status 等考试特有字段）和 `tasks`（总览页合并排序，`task_type='exam'`）。两处都存，改一处不同步另一处就会出现"总览页日期和课程页日期对不上"。

**决策**

- `exam_dates` 是**可编辑的权威源**。
- `tasks` 里 `task_type='exam'` 且 `source='syllabus'` 的记录是它的**派生缓存**，由后端在 exam 创建/编辑/删除时自动同步。
- 前端**不允许直接编辑**这类 task，只允许改 `exam_dates`。
- `tasks.source_id` 对考试指向 `exam_dates.id`，用于去重与增量同步。

**理由**

两张表各自职责清晰、都不该砍：`exam_dates` 承载考试特有的字段，`tasks` 保持轻量统一以便总览页合并排序。用"派生 + 自动同步"规则消除双写，比强行合并成一张表代价小。

这也天然呼应产品的"用户可编辑、可覆盖"原则——`exam_dates` 是用户可编辑层，`tasks` 是系统视图层。

**后果**

- 后端必须实现 exam_dates 变更 → tasks 同步的逻辑，这是新增的复杂度。
- 同步逻辑本身要有失败处理（见 ADR-005 的降级要求）。

**复审条件**

如果考试与任务的字段差异消失（tasks 能完整承载考试信息），可以考虑合并。

### ADR-005：同步轮询策略——前期宽松，后期收紧

- **状态**：已接受
- **日期**：2026-09-01

**背景**

syllabus 是静态的（一学期一份），但 Canvas 是动态的：due date 会改、会延期、作业会新增。老师把 deadline 从明天改到后天，Tempo 多久能知道，直接等于产品的体验命门——如果滞后 24 小时，学生可能刚好错过一个改到明天的 deadline，而"省心"是 Tempo 的全部卖点。

**决策**

- 采用**轮询**拉取（Phase 0 无 webhook 可用）。
- **前期轮询频率宽松**，大一点可接受，先验证"实时同步是否有价值"。
- 验证通过后，再优化为更精细的增量同步与变更检测。
- 具体数值在 `Sync-Strategy.md` 定义。

**理由**

Steven 明确授权"前期轮询频率稍微大一点都 OK，后期提上来"。MVP 阶段最重要的是验证价值假设，不是优化性能——在没证明"实时同步有人要"之前，把工程精力花在精细化同步上是浪费。

**后果**

- 必须设计：失败降级（同步失败要用户可见，不能静默）、token 过期提醒、增量更新而非全量覆盖。
- 后期用户量上升时，需注意 Canvas API 限流风险。

**复审条件**

用户量上升导致 API 限流；或用户反馈"变化发现太慢"；或进入 Phase 1 后可评估更优的变更检测机制。

### ADR-006：技术栈锁定 Next.js + Supabase

- **状态**：已接受
- **日期**：2026-09-01

**背景**

个人 / 小团队开发，需要服务数量尽可能少、迭代尽可能快。

**决策**

Next.js 全栈（App Router）+ Supabase（Postgres + Auth + Storage 三合一）+ Vercel 部署。详见 `TechStack.md`。

**理由**

Supabase 一家提供数据库、认证、文件存储三件套，减少了需要接入的服务数量。免费额度足够 MVP。Next.js 全栈让前后端同仓，适合快速迭代。

**后果**

- 受 Supabase 平台限制（Edge Function 约束、免费额度上限）。
- 部署绑定 Vercel。
- 换栈成本高，所以必须用 ADR 锁死，避免开发中途反复横跳。

**复审条件**

免费额度不够；或需要 Supabase 明确不提供的能力。

### ADR-007：明确不做 CalCentral 集成与 Gradescope / Piazza 自动提交

- **状态**：已接受
- **日期**：2026-09-01

**背景**

CalCentral 集成、Gradescope 自动提交、Piazza 自动回复这类功能看起来很有价值，但它们没有官方 API，依赖模拟登录或逆向工程。

**决策**

- **不做** CalCentral 集成（学校账号认证 + 无公开 API，难度与风险都不匹配投入产出比）。
- B2 类功能（无官方 API、依赖逆向、失败后果直接影响学业）**不作为产品能力**，仅作为长期实验性、**用户主动开启（opt-in）**的功能存在。
- B2 类功能**不进主流程、不作核心卖点宣传**，且必须有清晰的失败可见性。

**理由**

维护成本高（平台一改就挂）、失败后果严重（作业没交上）、且与学校官方合作路径直接冲突。核心卖点应该始终是"理解与规划"能力（Phase 0-2），不是"替你提交"。

**后果**

Tempo 的能力边界受官方 API 限制，某些学生痛点（如 Gradescope 提交流程）暂时覆盖不到。这是有意识的取舍。

**复审条件**

相关平台官方开放 API。

### ADR-008：ToS 风险与法律风险分开定性

- **状态**：已接受
- **日期**：2026-09-01

**背景**

早期文档里笼统地使用"法律风险"来描述各种合规问题，容易把问题想得比实际严重，导致决策误判（要么过度恐慌不敢做，要么掉以轻心）。

**决策**

明确区分两类风险，文档措辞不得混用：

| 类型 | 涉及场景 | 最坏后果 |
|---|---|---|
| **平台政策（ToS）风险** | Canvas PAT 接入 | Canvas 有权终止 API 访问、撤销 token、要求停止该接入方式 |
| **法律风险** | Phase 4 past paper 资源库（版权）、FERPA 隐私数据 | 真正的法律责任 |

**理由**

两者性质与量级完全不同。Canvas PAT 场景下，每个用户看到的都是自己账号本来就能看到的数据，不涉及第三方隐私泄露，不存在法律责任；而 past paper 的版权和 FERPA 才是需要认真评估法律后果的领域。

**后果**

- 文档措辞必须精确，看到"风险"要先分清是哪一类。
- Phase 4 的 past paper 需要在启动前**单独评估版权与 FERPA**，不能等做出来再补救。

**复审条件**

进入 Phase 4 规划时。

### ADR-009：syllabus 上传走浏览器直传 Supabase Storage，不走服务端转发

- **状态**：已接受
- **日期**：2026-09-02

**背景**

`API-Contract.md` 原定上传接口为 `POST /api/v1/courses/:id/syllabus`，`multipart/form-data` 由服务端 Route Handler 转发到 Supabase Storage，单文件上限 **20MB**（`TechStack.md` 第 4 节按 Storage 免费层 1GB 额度给出）。

但文件若经 Vercel 函数转发，会撞上平台的**请求体大小上限**——而 syllabus PDF 通常在 1-5MB，把设计上限从 20MB 砍到平台能接受的值，等于为了迁就部署平台而牺牲用户侧宽裕度。

**决策**

改为**浏览器直传**（browser → Supabase Storage），服务端只负责收尾建行：

```
① 前端校验类型/大小（仅体验层，不可信）
② 前端用 session 直传私有桶，路径 {user_id}/{course_id}/{uuid}.{ext}
③ POST /api/v1/courses/:id/syllabus  { fileName, storagePath, size }
④ 服务端校验路径归属（首段 = auth.uid()）+ 文件真实存在 + 类型 + 大小
⑤ 插 syllabi 行（extract_status=pending, parse_status=pending）
```

`API-Contract.md` §3 的 multipart 契约随之改写为两步式 JSON（在 P0-1-1 交付时同步更新，不单独拆 task）。

**理由**

- **保住 20MB 设计上限**，不为平台限制牺牲用户侧宽裕度。
- **不占 Vercel 函数时长与内存**：20MB 文件过服务端会显著吃掉 Hobby 层的资源预算，而直传是浏览器与 Storage 之间的事。
- **安全边界等价**：私有桶 + `storage.objects` 的 RLS 策略按「路径首段 = `auth.uid()`」判定，与服务端的授权强度一致——不是把校验交给前端，而是把校验交给 Storage 自己的 RLS。
- 后端仍然保留**权威校验**（步骤 ④）：前端校验只是体验层，路径归属、类型、大小在服务端再查一遍。

**后果**

- **契约文档要改**：`API-Contract.md` §3 与路由总表的 multipart 描述失效，需改写为两步式。
- **多一次往返**：直传 + 建行两次请求，失败点也变成两个。
- **孤儿文件**：直传成功但建行失败，会在桶里留下无主文件。Phase 0 接受这个代价，靠 P0-3-2「一键删除账号」按用户前缀整段清理；若将来孤儿文件堆积成问题，再补一个对账清理任务。
- **前端校验不能当权威**：这条写进代码评审清单——`size` 与扩展名由客户端上报，服务端必须复核。

**🔴 未实测项（诚实标注）**

本条 ADR 的主要论据「Vercel 平台对请求体存在约 4.5MB 上限（Hobby 层）」**来自既有认知，未经本次实测**。它在决策时用于判断"20MB 走服务端转发不可行"，但不影响决策本身的另一半理由（不占函数时长、保住用户侧上限）成立。

**若该数字被证伪（即平台实际允许更大请求体），不推翻本 ADR** —— 直传在资源占用上仍更优。但应回来更新本节，避免后人依据一个未验证的数字做判断。

**复审条件**

平台请求体上限放宽且需要"上传即解析"（服务端必须摸到文件内容）；或孤儿文件清理成本失控；或将来改为需要服务端改写文件内容（如压缩、转码）。
