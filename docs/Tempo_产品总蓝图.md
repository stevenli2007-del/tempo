## 北极星原则

> 学生的精力应该花在学习课程内容上，而不是花在理解课程规则、整理 deadline、搞清楚怎么交作业这些"元工作"上。

Tempo 的每一个功能、每一个技术决策，最终都要回答一个问题：**这件事是不是在替学生消化"元工作"，把省下来的精力还给真正的学习？** 如果一个功能不服务于这条原则，它就不该出现在 Tempo 里。

产品定位一句话总结：**Tempo 是学生的课程操作系统（Course OS）**——一个持续感知、动态管理、主动规划所有课程琐事的层，而不是又一个 to-do list app。

## 产品内核：实时检测 + 动态管理

> 这一节是 Tempo 的立身之本。**如果 Tempo 只做"翻译、整理、规划 syllabus"，它随时会被干掉。**

### 区分"表层"与"内核"

同样是"课程管理"这件事，有两层完全不同的东西：

| | 表层（可被替代） | 内核（Tempo 的命） |
|---|---|---|
| 做什么 | 翻译 syllabus、整理成表格、生成 study plan | **持续检测数据源变化、动态更新进度、按进度重新规划** |
| 交互形态 | 一次性：传一次文件，出一份静态结果 | **持续性：每天打开都有新状态** |
| 被替代的难度 | 低——随便一个 GPT 对话框就能做 | 高——取决于数据接入的深度与稳定性 |
| 用户价值 | "帮我省了 20 分钟" | **"我不用再天天去确认了"** |

**表层是入口，内核是留存。** syllabus 解析是让学生第一次觉得"哦这东西有用"，但真正让学生每天打开、并且离不开的，是后面那三件事。

### 内核的三件事

Tempo 的内核能力可以拆成一条闭环，缺一环就不成立：

```
   ① 实时检测                ② 动态管理                 ③ 动态规划
检测数据源变化  ──────▶  更新任务与进度状态  ──────▶  生成/调整每日任务
Canvas / CalCentral             冲突识别与合并              长期任务按天拆解
Google Calendar                 完成状态追踪                顺延与再分配
课程网页 / iCal                 过期信息清理
        ▲                                                        │
        └──────────────────── 闭环：进度变化反哺规划 ◀───────────┘
```

1. **实时检测（Detection）**：持续从多个数据源（Canvas、CalCentral、Google Calendar，以及部分课程特有的软件与网页）拉取变化——due date 被改、新作业发布、考试日期确认、任务被标记完成。
2. **动态管理（Management）**：把检测结果合并进统一的任务视图，处理来源冲突（syllabus 说周一、Canvas 说周三）、识别完成状态、清理过期信息。
3. **动态规划（Planning）**：基于**当前真实进度**而非初始计划，生成每日任务、把长期任务拆解到每天、把未完成项合理顺延。

### 为什么这个内核才是护城河

- **它依赖数据接入的深度，而不是界面的美观度。** 界面可以被抄，稳定接进十几个数据源并保持同步，抄不动。
- **它有复利效应。** 跑得越久，积累的"这门课的节奏模式"越准，规划质量越高，用户越难迁移。
- **它天然对抗"一次性工具"的宿命。** 静态整理工具用完一次就走，实时系统每天都在产生价值。

> **产品判断（写进所有下游文档的共识）**：任何功能提案，先问它服务于闭环中的哪一环。只服务"表层"的功能，除非是冷启动必需的入口，否则优先级一律排在内核能力之后。

## 为什么是蓝海：竞品与替代方案

Tempo 面对的**不是竞争对手，而是"学生的手动土办法"**。理解这一点，决定了 Tempo 该怎么定位自己。

### 学生现在在怎么做

| 替代方案 | 学生怎么用它 | 为什么不够 |
|---|---|---|
| **手动问 ChatGPT** | 把 syllabus 丢进对话框，让它总结重点、列个表 | 一次性、无记忆；问完就散落在聊天记录里；下次还要重新贴一遍；**它不知道你的 deadline 昨天被改了** |
| **Notion / 手写表格** | 自己建数据库，一学期维护一次 | 维护成本高到大多数人两周后就放弃；**纯手动，不会自己更新** |
| **Google Calendar** | 手动把 deadline 敲进日历 | 只解决"什么时候"，解决不了"怎么交、占多少分、规则是什么"；录入本身就是元工作 |
| **Canvas 自带 To-Do / 日历** | 官方视图 | 只覆盖 Canvas 自己；不含 syllabus 里的评分构成、考试安排、提交规则；**跨课程没有统一规划** |
| **Notion Calendar / Sunsama 等通用工具** | 通用任务管理 | 不是为课程设计的，不懂 grade weight、不懂 syllabus 结构、**不接学校数据源** |

### 结论：这不是红海竞争，是"没人认真做过"

Steven 的一手观察（2026-09）：**身边同学整理 syllabus、规划学习，普遍是"手动问 AI + 四处找资料"，非常麻烦。**

成立的原因很清楚：

1. **难的不是界面，是数据接入。** 通用工具厂商不会为一所学校去接 Canvas，学校自己做的系统又只覆盖自己那一块。**中间的翻译层 + 对齐层，是空的。**
2. **这件事的边际成本结构不适合大公司做。** 每所学校、甚至每门课的数据源都不一样，属于"看起来不大、做起来很碎"的活，大厂看不上，学生做不了，独立开发者嫌麻烦——**这恰好是个人项目的机会窗口**。
3. **AI 让"翻译非结构化文本"这件事的成本断崖式下降。** 三年前做这件事，光解析 syllabus 就够一个团队；现在这变成了几百行代码。技术窗口刚刚打开。

### 因此 Tempo 的竞争策略

**不与通用工具比功能全面，只比"对课程的接入深度"。**

- 不和 Notion 抢"任务管理"，只做"课程这一件事做到别人做不到的深度"。
- 不和 Canvas 官方抢"权威数据源"，只做"官方视图没有的那一层整合与规划"。
- 冷启动阶段**几乎没有直接竞品**，因此 Phase 0 的成功标准是"学生愿不愿意从手动土办法切换到 Tempo"，而不是"Tempo 比某个竞品好在哪"。

> **复审条件**：若出现以下任一情况，需重新评估蓝海判断——① 主流通用工具（Notion / Google）开始官方接入 Canvas 并做课程场景；② 出现 2 个以上直接竞品且已跑在 Tempo 前面；③ 伯克利官方推出同类整合视图。

## 战略主线：从"只读"到"代理"的信任阶梯

整个产品的发展路径，本质上是一条**信任阶梯**：先证明"我能看懂、看全你的课程世界"，再逐步证明"我能替你做一些事而不出错"。这条阶梯不能跳步——每一层都要先建立可靠性，才能往上走。

```
Phase 0: 感知闭环的最小验证  →  syllabus 结构化 + Canvas/日历只读同步 + 手动刷新
Phase 1: 正式动态感知层      →  Canvas 升级为官方 OAuth，接入 Google Calendar，自动定时同步
Phase 2: 规划智能层          →  跨课程整合，每日任务生成与动态调整（内核成型）
Phase 3: 轻量代理层          →  官方 API 支持的"写"操作
Phase 4: 生态与资源层        →  资源 hub、社区数据、深度代理（谨慎）
```

> **更新说明**：原计划 Canvas 集成放在 Phase 1，但经过技术验证，伯克利 bCourses 允许学生自行生成 Personal Access Token（无需机构审批），因此把"Canvas 只读同步"提前纳入 Phase 0 MVP。这个调整不改变信任阶梯的逻辑，只是让 MVP 阶段就能验证"实时检测"这个内核能力，而不用等到 Phase 1。详见 [ADR-002](./Decisions.md#adr-002)。

### 同步延迟是命门（贯穿 Phase 0-2 的第一优先级问题）

**Tempo 卖的是"省心"，而省心的前提是学生敢信 Tempo 上的数据是最新的。** 这意味着同步延迟不是性能指标，是**产品可信度指标**：

- 老师把 deadline 从明天改到后天，Tempo 多久知道？
- 新作业发布了，学生多久能在 Tempo 看到？
- 如果滞后 24 小时，学生可能刚好错过一个改到明天的 deadline——**一次这样的失误，就足以让"省心"这个卖点归零。**

**策略**：前期轮询频率放宽（优先保证"数据一定是最新的"这个体验），后期再按成本优化收紧。具体轮询频率、变更检测、增量同步、失败降级方案见 [`Sync-Strategy.md`](./Sync-Strategy.md)，策略依据见 [ADR-005](./Decisions.md#adr-005)。

## Phase 0：感知闭环的最小验证（MVP）

**目标**：验证两件事——① 学生愿意上传 syllabus 且认可 AI 解析的价值；② "任务自动同步 + 进度自动更新"这个内核体验是否真的让人更省心。

### 里程碑拆分（按顺序交付，逐个验收）

| 里程碑 | 内容 | 验证的问题 | 风险 |
|---|---|---|---|
| **M1** | syllabus 上传 + 解析 + 可编辑表单 | 表层价值：解析结果比自己啃 syllabus 更省心 | 低，无合规风险 |
| **M2** | 数据源同步（**Canvas PAT**，入口已实测可用）+ 课程手动关联 + 合并总览 | 内核价值：自动同步是否减少打开 Canvas 的次数 | 低（原"中，依赖 token 可用性"，P0-2-1 实测已排除） |

> **为什么拆两段**：M2 涉及加密存储、服务端代理、token 过期提醒、失败降级——出错面远大于 M1。先跑 M1，即便 M2 出问题，核心验证也不受拖累。
>
> ✅ **拆分顺序已被验证是对的**：2026-09-01 实测确认 bCourses 学生 token 入口可用（P0-2-1），PAT 路线成立，M2 最大的不确定性已排除。iCal Feed 保留为长期 Plan B，不再是 Phase 0 的工作项。

**核心功能**
- Workspace 创建（semester + 课程名 + 可选课程编码/教师）
- Syllabus 上传（PDF / Word / PPT）→ LLM 结构化解析五大板块：
  - Grade Composition
  - Course Outline
  - Test Dates（允许 TBD 状态）
  - Office Hours
  - Submission Policy
- 解析结果 → 可编辑表单，用户核对/修正（**这一步的用户修正数据是未来优化 prompt 的种子数据，从第一天就要存成"原始解析 vs 修正后"的 diff**，否则将来是一堆没法用的散数据）
- **数据源同步（M2）**：
  - **主路径**：用户在设置页手动粘贴自己在 bCourses 生成的 Personal Access Token（附图文教程）
  - **Plan B**：若 token 入口不可用，改用 Canvas Calendar Feed（iCal 私有链接）读取作业 due date，功能降级但合规且够用
  - 拉取用户的 Canvas 课程列表与作业 due date
  - 用户手动将 Canvas 课程与 Tempo Workspace 关联（不做自动匹配，避免匹配错误；Phase 1 再引入匹配辅助）
  - 关联后，Canvas 作业自动出现在对应 Workspace 的任务列表中
  - **Token 有效期 90 天（学生 token 强制填过期时间，2026-09-04 P0-2-1b 实测）**，到期前基于用户实际填写的过期时间提醒重新生成
  - 提供"撤销授权"入口，用户随时可断开
- **手动刷新 + 自动定时轮询**：轮询频率前期放宽，优先保证数据新鲜度（详见 [`Sync-Strategy.md`](./Sync-Strategy.md)）
- 基础总览页：各课程卡片 + 关键日期一览（合并 syllabus 考试日期 + Canvas 作业 due date）

**技术要点**
- PDF/Word/PPT 文本提取；扫描件/复杂排版走"抽不出就提示用户手动补"的降级，不为此单独引入 OCR 管线（详见 [ADR-003](./Decisions.md#adr-003)）
- LLM 走**可插拔 provider 抽象层**，默认 DeepSeek，效果不达标可切 Claude 而不动业务代码
- 结构化输出走 JSON schema，五个板块拆成独立抽取任务，而非一次性丢一个大 prompt，降低出错率
- 数据模型每个字段都要支持"未知/待补充"状态，不能假设一定能抽出来
- Canvas 凭据必须**加密存储**，所有对 Canvas API 的请求都在**服务端**发起，不暴露给前端

**关于 Personal Access Token 的定位**：这是**验证期的临时手段，不是长期方案**。它不经过机构审批，今天就能做，但用户需手动复制粘贴，门槛高，不适合大规模推广——这恰好匹配 MVP"用一小批愿尝鲜的种子用户验证核心价值"的定位。等验证通过、需要向更广泛学生群体推广时，**必须**投入 Phase 1 的正式 OAuth 流程。

**风险定性（重要）**：Canvas PAT 涉及的是**平台政策（ToS）风险**，最坏后果是 Canvas 撤销 token 或终止接入，**不涉及法律责任**。它与 Phase 4 的 UGC 版权 / FERPA 隐私属于**完全不同量级的两类风险**，不可混为一谈。5-6 人自用规模下，实际风险趋近于零。分级标准见 [`Security-Privacy.md`](./Security-Privacy.md)，依据见 [ADR-008](./Decisions.md#adr-008)。

**成功标准（量化）**

| 指标 | 定义 | 为什么用它 |
|---|---|---|
| **编辑修正率** | 上传过 syllabus 的课程中，用户主动编辑/修正过解析结果的比例 | 验证"AI 解析 + 人工核对"闭环真的在发生，而不是用户看都不看就保存 |
| **7 日回访次数** | 关联数据源后 7 天内，用户主动打开总览页的次数 | 直接量化"自动同步是否减少了打开 Canvas 的次数" |
| **人均关联课程数** | 完成数据源关联的课程数量 | 关联数低说明接入门槛过高，或匹配体验有问题 |
| **token 续期完成率** | 收到过期提醒后完成重新授权的比例（M2 后期观察） | 衡量"手动授权"这个摩擦的长期可接受度 |

定性补充：用户主观反馈"确实减少了打开 Canvas 确认信息的次数"。

## Phase 1：正式动态感知层

**目标**：把 Phase 0 验证过价值的"实时检测"能力，升级成面向所有学生的正式接入方式，并把数据源从 Canvas 扩展到 Google Calendar 等。

**核心功能**
- **Canvas 升级为 OAuth2 正式集成**：向伯克利申请 Developer Key（机构审批），实现一键授权，替代手动粘贴 token；同时可拿到比 PAT 更完整的数据（提交状态、成绩等）
- **Google Calendar OAuth 集成**：读取/写入日程，实现"考试日期自动同步到你的日历"
- **更多数据源接入（按优先级排，逐个评估）**：
  - Canvas Calendar Feed（iCal）—— 兜底与交叉验证
  - 课程网页抓取兜底（LLM 判断页面是否有新信息）
  - **CalCentral**——**明确不做**（学校账号认证 + 无公开 API，投入产出比不匹配，见 [ADR-007](./Decisions.md#adr-007)）
- 同步升级为**自动定时轮询 + 变更检测**（新任务、due date 变更、成绩更新），不再是手动刷新
- 任务关联从"用户手动关联"升级为自动匹配辅助（**仍保留人工确认环节**）

**技术要点**
- 标准 OAuth2，scope 严格限制在 read
- **增量同步 + 变更检测**是这一阶段的工程核心，不能每次全量拉取
- 网页抓取兜底方案必须对用户明确"不保证稳定"的预期管理
- **机构审批周期长，应在 Phase 0 初见成效时就同步启动申请流程**，不要等 Phase 0 完全结束才联系伯克利——此时手里已有真实用户与数据，谈判筹码完全不同

## Phase 2：规划智能层（内核成型）

**目标**：从"给你看数据"进化到"帮你做决定"——这是内核闭环的第三环，也是最容易做得"看起来聪明实际很蠢"的一层，需要谨慎打磨。

**核心功能**
- 总览页可视化升级：动态进度条、时间线视图
- **每日任务自动生成**：综合所有课程的近期任务，按权重（grade weight、剩余时间、任务类型）排序
- **大项目任务分解**：LLM 根据任务描述和 deadline 生成子任务时间线，把长期任务拆解到每天
- **动态调整**：当天未完成任务的合理顺延（均摊到后续几天，而非全部堆到明天），支持用户手动拖拽调整
- **进度感知**：基于同步到的完成状态追踪进度，而非基于初始计划空转

**技术要点**
- 任务排序算法需要**可解释**（用户要理解"为什么今天先让我做这个"），不能是黑盒推荐
- 分解逻辑要谨慎，不同课程、不同学生的节奏差异很大，避免"一刀切"显得不了解学生实际情况
- 顺延逻辑必须给用户可控性，纯自动堆积容易造成"任务爆炸"的负面体验
- **规划的输入是实时检测到的真实进度**——这一层的质量上限，取决于 Phase 0/1 的同步延迟与数据完整度

**成功标准**：用户开始把 Tempo 的每日任务列表当作"今天真正要做的事"的唯一入口，而不是仍然要回到 Canvas 再确认一遍。

## Phase 3：轻量代理层（谨慎推进）

**目标**：在官方 API 支持的范围内，让 Tempo 从"告诉你该做什么"进化到"替你做一部分事"——但严格限定在**有官方支持、可回滚、可验证**的操作范围内。

**核心功能（示例）**
- 自动创建 Google Calendar 事件（考试提醒、任务 deadline）
- 如果学校/Canvas 未来开放更多写权限（比如标记任务完成状态），可考虑接入

**分级原则（重要）**
- **B1：低风险**——有官方 API 支持写操作的场景，复杂度接近 Phase 1，可以较早做
- **B2：高风险**——无官方 API 的平台（如 Gradescope 自动提交、Piazza 自动回复），依赖模拟登录/逆向工程，维护成本高、失败后果直接影响学业、且与学校官方合作路径相冲突

**明确态度**：B2 类功能不是"不做"，而是作为**长期实验性、用户主动开启（opt-in）**的功能存在，且必须有清晰的失败可见性（比如"已提交成功"要有实证展示，不能让用户完全放手不管）。这类功能不应该出现在主流程里，更不应该被当作 Tempo 的核心卖点来宣传——核心卖点应始终是 Phase 0-2 的"实时检测 + 动态管理 + 规划"能力。

---

## Phase 4：生态与资源层

**目标**：从"个人工具"进化到"学生共享的知识生态"，同时是长期的护城河所在——因为这一层积累的是**跨用户、跨学期的数据资产**，这是纯粹做"工具"的产品很难建立的壁垒。

**核心功能**
- Past exam / past paper 资源库（需要认真设计内容来源机制——UGC 用户共享上传 vs 官方合作，两条路径的版权风险完全不同，UGC 模式必须有明确的版权免责与举报机制）
- 课程/教授评价整合
- 跨学期数据沉淀：同一门课不同学期的 syllabus 变化趋势、任务节奏模式，可以反过来提升 Phase 0 的解析准确率和 Phase 2 的规划智能

**注意事项**：这一层涉及**真正的法律风险**（UGC 版权 + FERPA 隐私），与 Canvas PAT 的平台政策风险**性质完全不同**，不可混谈。启动前单独评估，而不是等做出来了再补救。详见 [`Security-Privacy.md`](./Security-Privacy.md)。

---

## 贯穿所有阶段的设计原则

1. **信任优先于智能**：一个"每次都对但偶尔完全失控"的功能，比一个"稳定普通但从不出错"的功能更危险。尤其是 Phase 3 涉及"写"操作时，可靠性的优先级永远高于功能的酷炫程度。
2. **允许"不知道"**：数据模型从 Phase 0 开始就要接受信息不全、来源冲突、暂时无法解析的情况，不要假设系统总能给出确定答案。**AI 解析禁止编造**——一次编造就足以摧毁产品的信任基础。
3. **用户可编辑、可覆盖**：任何 AI 生成/抓取的信息，用户都应该能够看到、修正、覆盖。这既是产品体验的安全网，也是持续优化模型的数据来源。
4. **读写分离的工程严谨度**：只读功能追求"覆盖面广、迭代快"，写操作追求"少而稳、每一步可验证、可回滚"，两者不能用同一套开发节奏对待。
5. **学校关系是战略资产，不是事后考虑**：越往 Phase 3、Phase 4 走，越需要考虑"这个功能会不会让学校官方觉得 Tempo 是在帮学生投机取巧、绕过系统"。长期看，能被学校认可甚至合作推荐的产品，比单纯技术上更强但游走在灰色地带的产品更有生命力。
6. **内核优先于表层**（新增）：当"做一个漂亮的整理功能"和"让同步更及时、更可靠"冲突时，**永远选后者**。表层决定用户会不会来，内核决定用户会不会留。

## 各阶段验证的核心问题

| 阶段 | 要验证的核心假设 |
|---|---|
| Phase 0 | 学生愿意上传 syllabus 且认可 AI 解析价值；数据源自动同步确实减少了打开 Canvas 的次数；同步延迟在可接受范围内 |
| Phase 1 | 升级为一键 OAuth 授权后，能否触达更广泛、不愿手动折腾 token 的学生群体 |
| Phase 2 | 学生真的会把 Tempo 的每日任务列表当作行动的唯一入口 |
| Phase 3 | 在官方支持范围内的"代劳"操作，能否在不牺牲可靠性的前提下带来足够价值 |
| Phase 4 | 跨用户数据沉淀能否形成足够强的网络效应，让 Tempo 从"工具"变成"平台" |
