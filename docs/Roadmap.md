## 3. 内核能力成熟度阶梯

Tempo 的内核是「实时检测 → 动态管理 → 动态规划」。这张表说明**每个 Phase 结束后，内核应该达到什么水平**——它是比功能清单更重要的进度衡量标准。

| 能力维度 | Phase 0 | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|---|
| **数据源覆盖** | Canvas 一条（+ iCal 兜底） | Canvas OAuth + Google Calendar + 网页兜底 | 同 Phase 1 + 完成状态追踪 | 同 Phase 2 |
| **同步触发** | 手动刷新 + 宽松定时轮询 | 自动定时轮询 + 变更检测 | 同 Phase 1 | 同 Phase 1 |
| **同步延迟** | 分钟级（前期频率放宽） | 分钟级，按成本优化 | 分钟级 | 分钟级 |
| **变更处理** | 覆盖式更新 | **增量同步 + 变更检测** | 同 Phase 1 + 冲突识别 | 同 Phase 2 |
| **进度感知** | 有 deadline，无完成状态 | 有提交状态 | **追踪完成状态** | 同 Phase 2 |
| **规划能力** | 按时间顺序排列 | 同 Phase 0 | **权重排序 + 任务分解 + 顺延** | 同 Phase 2 |
| **代理能力** | 无 | 无 | 无 | **B1 类写操作** |

> **判断原则**：功能可以做加法，但内核能力**不能跳级**。若 Phase 1 的增量同步没做好就去做 Phase 2 的规划，规划的输入是脏数据，做出来只会"看起来聪明实际很蠢"。

## 5. Phase 1 — 正式动态感知层

**状态**：⚪ 未开始 ｜ **依赖**：Gate 0→1 通过

**核心命题**：能不能让**不想折腾 token 的普通学生**也无痛接入，并把数据源铺开。

**关键交付**
- Canvas OAuth2 正式集成（伯克利 Developer Key 机构审批）
- Google Calendar OAuth 集成（读/写日程）
- 自动定时轮询 + **增量同步与变更检测**
- Canvas Calendar Feed（iCal）兜底与交叉验证
- 课程自动匹配辅助（**保留人工确认**）
- 课程网页抓取兜底（明确告知用户不保证稳定）

**主要风险**
- **机构审批周期长**（最大风险）→ **缓解：Phase 0 初见成效时立即启动申请，不等 Phase 0 结束**。此时手里有真实用户与数据，谈判筹码完全不同
- 增量同步的变更检测做不好 → 直接卡住 Phase 2（规划依赖干净的输入）
- Scope 过大引发学校顾虑 → 严格限制在 read

**明确不做**：CalCentral 集成（[ADR-007](./Decisions.md#adr-007)）

### Gate 1→2

| # | 条件 |
|---|---|
| G1-1 | OAuth 一键授权流程可用，非技术用户能独立完成 |
| G1-2 | 增量同步 + 变更检测稳定（能正确识别 due date 变更、新作业发布） |
| G1-3 | 至少 2 个数据源同时工作且数据一致（无日期打架） |
| G1-4 | 同步延迟在用户可接受范围内（无"错过 deadline"反馈） |
| G1-5 | 用户规模较 Phase 0 有实质增长（不再限于愿折腾的同学） |

## 6. Phase 2 — 规划智能层（内核成型）

**状态**：⚪ 未开始 ｜ **依赖**：Gate 1→2 通过

**核心命题**：学生会不会**照着 Tempo 给的计划行动**，而不是看完再回 Canvas 确认一遍。

**关键交付**
- 每日任务自动生成（按 grade weight / 剩余时间 / 任务类型加权排序）
- 大项目任务分解（长期任务拆解到每天）
- 动态调整：未完成任务合理顺延（均摊而非堆积），支持手动拖拽
- 进度感知：基于同步到的**真实完成状态**而非初始计划
- 总览页可视化升级：动态进度条、时间线视图

**主要风险**
- 排序黑盒 → 用户不理解"为什么先做这个" → **可解释性是硬要求**
- 一刀切的分解逻辑显得不了解学生实际节奏 → 需支持个性化调整
- 顺延堆积造成"任务爆炸" → 必须给用户可控性

### Gate 2→3

| # | 条件 |
|---|---|
| G2-1 | 用户把 Tempo 每日任务列表当作"今天要做的事"的唯一入口 |
| G2-2 | 排序结果可解释，用户能理解优先级理由 |
| G2-3 | 顺延逻辑未引发"任务爆炸"的负面反馈 |
| G2-4 | 规划输入来自真实同步进度（而非静态计划） |

## 7. Phase 3 — 轻量代理层（谨慎推进）

**状态**：⚪ 未开始 ｜ **依赖**：Gate 2→3 通过

**核心命题**：在官方 API 支持范围内，敢不敢让 Tempo 替你动手。

**分级**
- **B1（低风险，优先做）**：有官方 API 支持的写操作，如自动创建 Google Calendar 事件
- **B2（高风险，opt-in 实验）**：无官方 API 的平台（Gradescope 自动提交、Piazza 自动回复）

**B2 的三条铁律**（总蓝图已定，此处重申）
1. 用户**主动开启**（opt-in），不进主流程
2. 必须有**清晰的失败可见性**（"已提交成功"要有实证展示）
3. **不作为核心卖点宣传**——核心卖点始终是 Phase 0-2 的实时检测与规划

### Gate 3→4

| # | 条件 |
|---|---|
| G3-1 | B1 类写操作成功率稳定，且失败可回滚 |
| G3-2 | 无任何"因为相信 Tempo 而误事"的事故 |
| G3-3 | 学校官方未对 Tempo 提出合规质疑 |

## 8. Phase 4 — 生态与资源层

**状态**：⚪ 未开始 ｜ **依赖**：Gate 3→4 通过

**核心命题**：跨用户数据沉淀能否形成网络效应，让 Tempo 从工具变成平台。

**关键交付**
- Past exam / past paper 资源库（UGC vs 官方合作两条路径）
- 课程/教授评价整合
- 跨学期数据沉淀（反哺 Phase 0 解析准确率与 Phase 2 规划智能）

**主要风险**
- **真正的法律风险**（UGC 版权 + FERPA 隐私），与 Canvas PAT 的 ToS 风险**性质完全不同**，启动前单独评估（[ADR-008](./Decisions.md#adr-008)）
- 网络效应起不来的冷启动问题

## 9. 学期节奏约束（重要）

Tempo 的验证强依赖**学期周期**——这是纯技术项目没有的硬约束，规划时必须考虑：

| 约束 | 影响 |
|---|---|
| **Fall 2026 学期正在进行中**（当前 2026-09） | Phase 0 必须在本学期内跑完，否则要等 Spring 2027 才有真实课程数据，验证窗口直接推后 4 个月 |
| **期中（约 10 月）是 syllabus 价值的峰值** | 考试日期、评分构成的关注度在学期初和期中最高，Phase 0 应赶在这个窗口前上线 |
| **期末（约 12 月）是"每日任务"价值的峰值** | Phase 2 的规划能力若在期末前上线，验证效果最好 |
| **学期初（1 月 / 8 月）是获客窗口** | 学生重新整理课程的动机最强，规模化动作应对齐学期初 |
| **寒暑假是数据真空期** | 不适合做验证，适合做工程重构与下一阶段准备 |

**推论**：
1. **Phase 0 的核心价值验证应优先于工程完善**——错过 Fall 2026 这个窗口，代价不是一个 sprint，是一个学期。
2. **Phase 1 的 OAuth 申请时机（Steven 拍板 2026-09-01：不提前，等验证结果）**
   - 原建议是"并行申请以节省时间"，Steven 决定**改为串行**：申请策略与说辞应基于 Phase 0 的真实用户数据，空手去谈的筹码远不如带着结论去谈。
   - ⚠️ **代价**：Phase 1 的 OAuth 大概率赶不上 Fall 2026 学期。
   - ✅ **约束**：Gate 0→1 评审通过后**必须立即启动申请**，不得继续拖延——到那时这一条的代价就从"晚一点"变成"再损失一个学期"。
3. **不要在期末做破坏性重构**——用户正在依赖 Tempo 备考。
