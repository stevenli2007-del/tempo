# Sync-Strategy.md — Tempo 同步与检测策略

> **这份文档是 Tempo 的命门。** 产品内核是「实时检测 + 动态管理」，检测靠的就是同步。**同步滞后 = 产品价值归零** —— 学生因为信任 Tempo 而不去开 Canvas，结果 Tempo 自己也没更新，那一次失误足以让他不再打开这个应用。
>
> 本文件定义：**多久同步一次、同步什么、怎么判断变了、失败了怎么办、用户看到什么**。
> 数据怎么写见 `Database.md`，后端接口见 `API-Contract.md`，技术选型约束见 `TechStack.md`。

---

## 1. 三条不可协商的原则

| # | 原则 | 违反后果 |
|---|---|---|
| S1 | **永远不把旧数据伪装成新数据。** 任何展示任务的地方都必须能看到"最后同步时间" | 学生误以为看到的是最新的，错过改了时间的 deadline |
| S2 | **失败必须可见。** 同步失败要显示原因，不允许静默降级 | 同上，且排障时无从下手 |
| S3 | **同步不能破坏用户的手动状态。** 用户标记的"已完成"永远不能被同步覆盖 | 用户不再相信自己的操作有意义 |

## 2. 平台硬约束（2026-09 实测，不要凭印象改）

| 约束 | 实测值 | 对 Tempo 的影响 |
|---|---|---|
| **Vercel Hobby Cron 频率** | 每个 cron job **每天只能运行一次**；比"每天一次"更频繁的表达式会**导致部署失败**（Dashboard 不报错，只有 CLI 才显示） | 不能靠平台 cron 做小时级轮询 |
| **Vercel Cron job 数量** | 每项目 **100 个**（各 plan 相同） | ✅ **可以定义多个"每天一次"的 job，实现一天多次定点扫描** —— 这是被忽略的可用空间 |
| **Vercel Cron 触发精度** | **±59 分钟**，且调度时间只能写 UTC，无时区字段 | 兜底扫描对精度不敏感，可接受漂移 |
| **Vercel Function 时长** | Hobby 默认/上限均 **300 秒** | 单次同步预算要远低于此 |
| **Supabase 免费层** | **1 周无活动自动暂停** | 每日 cron 会读写数据库，**顺带解决保活问题**（重要副作用） |
| **Canvas 限流机制** | 动态令牌桶，响应头带 `X-Request-Cost` / `X-Rate-Limit-Remaining`，超限返回 **429** | 需要处理 429 + 退避 |
| **Canvas 并发惩罚** | 官方文档原文：*"any API client that makes no more than **one simultaneous request** is unlikely to be throttled. **Parallel requests are subject to an additional pre-flight penalty**"* | 🔴 **同步必须串行执行，禁止 `Promise.all` 并发拉课程** |

> 最后一条是本轮查证最有价值的发现：**并发拉 Canvas 会被额外惩罚**。直觉上"6 门课一起拉更快"是错的 —— 串行反而更快、更不容易触发限流。

## 3. 同步触发机制（四档）

| 档 | 触发方式 | Phase 0 频率 | 作用 | 优先级 |
|---|---|---|---|---|
| **T1** | **打开应用时同步** | 每次冷启动 / 页面重新获得焦点（距上次 ≥ 60s） | **主力。** 保证用户看到的永远是最新的 | 最高 |
| **T2** | **用户手动刷新** | 点击刷新按钮（节流 30s） | 给用户"我现在就要确定"的控制感 | 高 |
| **T3** | **平台定时兜底** | 每天 2 次定点（见 3.1） | 捕捉用户没打开期间的变化；**顺带保活 Supabase** | 中 |
| **T4** | **外部调度器** | 每 60 分钟（Phase 0 前期开启，可选） | 把"未打开期间"的滞后压到 1 小时内 | 可选 |

**核心判断**：Tempo 是**低频使用、高频依赖**的应用 —— 用户一天打开 2-3 次，而"打开时看到的是不是最新"才是体验命门。**T1 用零成本直接解决新鲜度问题**；T3/T4 解决的其实是另一个问题：**用户没打开时也要知道变化**（那是通知与后台一致性的需求）。想清楚这个区分，就不会把资源错配在无脑轮询上。

### 3.1 T3 平台定时的具体配置（两条 cron，利用"100 个 job"的空间）

```jsonc
// vercel.json —— 两条，各每天一次。UTC 时间，触发精度 ±59 分钟
{
  "crons": [
    { "path": "/api/v1/sync/scheduled", "schedule": "0 10 * * *" },  // 03:00 PDT 深夜扫描
    { "path": "/api/v1/sync/scheduled", "schedule": "0 22 * * *" }   // 15:00 PDT 午后扫描
  ]
}
```

- **03:00 PDT（10:00 UTC）**：捕捉前一天白天/傍晚的 deadline 变更，学生早上打开时数据已是新的。
- **15:00 PDT（22:00 UTC）**：捕捉当天上午的变更。课程变更最常发生在白天办公时间，课后（17:00+）再扫一次意义不大，因为学生打开时就同步了。
- **夏令时漂移**：11/1/2026 起 PDT→PST，cron 写的是 UTC，会整体漂移 1 小时（变成 02:00 / 14:00 本地）。**接受漂移**，兜底扫描对精度不敏感，不为此加复杂度。
- **保活副作用**：每天两次的函数执行会读写 Supabase，避免免费项目因一周无活动被自动暂停。这一条比它看起来重要 —— 否则寒暑假回来会发现项目停了。

### 3.2 T4 外部调度器（Phase 0 前期开启，Steven 已授权前期频率放宽）

用 cron-job.org（或 GitHub Actions schedule）每 60 分钟请求一次自有接口：

```
GET https://<domain>/api/v1/sync/scheduled
Authorization: Bearer ${CRON_SECRET}
```

- 接口用**恒定时间比较**校验 `CRON_SECRET`，缺失或错误直接 401。
- **不需要升级 Vercel** —— 平台限制的是它自己的调度器，不是我们的接口。
- 后期按第 11 节的数据收紧或放开。

## 4. 一次同步做什么（Pipeline）

```
1. 取锁        → sync_runs 中该用户有 status='running' 且 started_at > now()-5min？跳过本次
2. 读凭证      → 取出并解密 canvas_credentials.secret_encrypted
3. 校验状态    → status ≠ 'active'？直接结束，不动数据（不浪费 Canvas 请求）
4. 目标课程    → 已关联 && 未归档的课程（无 → 结束，一个请求都不发）
5. 节流        → 只有确定要发请求时才校验间隔（位置见下方说明）
6. 逐课拉取    → GET /api/v1/courses/:id/assignments           （N 个请求，串行！）
7. 变更比对    → 与库内比对，只写真正变了的
8. 落库收尾    → 更新 courses.last_synced_at / sync_status / sync_error；写 sync_runs；释放锁
```

> **✅ 2026-09-04 P0-2-5 落地时删掉了原第 4 步的 `upcoming_events` 主扫描**（Steven 拍板）。
> 原文称它是"关键优化"（1 个请求拿到全部课程的近期事件），实测与推敲后有两条反证：
> ① 它**只返回未来的事件**。逾期未完成的作业是总览页最该被看见的信号，
> 走这条路会系统性丢失它们 —— 与 Tempo「不隐藏问题」的原则直接冲突。
> ② 它**不带 `updated_at`**，做不了第 4.2 节的变更判定，逐课详情**依然非拉不可** ——
> 那个"1 个请求"省不下来，只是多出一个需要合并的数据源（以及"两个源不一致时信谁"的问题）。
> Phase 0 六门课 7 个请求，远在 20 个的预算内，这个优化此时是净负债。
> 若将来课程数涨到几十门，正确的优化方向是**按课程错峰 / 增量拉取**，不是加一个会丢数据的数据源。

**原来的"课程数保护 > 8 门跳过详情"随之作废**：没有主扫描可退守，改为第 6 节的三级熔断
（20 请求 / 60 秒 / 单课 3 页）统一兜底 —— 超预算时剩下的课留到下一轮，整批标 `partial`。

> **⚠️ 第 5 步节流的位置是刻意排在这里的**（P0-2-5 实测踩到后才定的）。
> 早先把它排在最前面，结果是：**token 已失效的用户点同步，看到的是"同步太频繁，27 秒后重试"**
> —— 真正该做的是重新生成 token。节流保护的是 Canvas 的限流额度，
> **一个请求都不会发的时候（没连接 / 凭证失效 / 没有可同步的课）回 429 是错误引导**。
> 排在这个位置，每种返回都指向用户真正能做的那个动作。

**分页**：`per_page=100`，若响应 `Link` 头含 `rel="next"` 则翻页，单课程最多翻 3 页。

## 5. 数值汇总表（改任何一个都要回来改这张表）

| 项 | 数值 | 依据 |
|---|---|---|
| T1 自动同步最小间隔 | **60 秒** | 防止刷新刷爆 Canvas |
| T2 手动刷新最小间隔 | **30 秒** | 手动是明确意图，放宽 |
| T3 平台定时 | **每天 2 次**（10:00 / 22:00 UTC） | Vercel Hobby 每 job 每天 1 次 |
| T4 外部调度 | **60 分钟** | Phase 0 前期授权放宽 |
| 单请求超时 | **10 秒** | Canvas 偶发慢响应 |
| 单次同步总预算 | **60 秒** | Vercel 上限 300s，留 5 倍余量 |
| 单次同步 Canvas 请求上限 | **20 个** | 熔断，防失控 |
| 单用户每日 Canvas 请求上限 | **300 个** | 熔断，超出则跳过并标记 `partial` |
| 同步锁超时 | **5 分钟** | 超过视为上次异常终止，强制释放 |
| 陈旧告警阈值 | **> 24 小时**未成功同步 → 总览页顶部警告 | S1 原则 |
| Token 过期提醒 | **T-14 / T-7 / T-3 / T-1 / 当天** | 给学生足够的重新生成窗口 |
| 并发度 | **1（严格串行）** | Canvas 对并发有 pre-flight 惩罚 |
| 资料区（P0-3-19）单课请求数 | **2 个**（`/files` + `/folders`，先 files 后 folders） | 实测 6 门课 = 12 个，在 20 预算内 |
| 资料区重扫间隔 | **24 小时**（手动刷新除外） | 目录低频变化，保住 20 请求预算给作业 |
| 大纲漂移（P0-3-20）额外 Canvas 请求 | **0 个** | 同步侧只读 `course_files` + 比锚点；真正的文件下载发生在**用户打开消息栏之后**，不占同步预算 |

### 用量估算（Phase 0，6 名用户）

| 项 | 计算 | 结果 |
|---|---|---|
| 单用户单次请求数 | 1 + 5 门课 | ≈ 6 |
| 单用户日请求量 | 打开 3 次 + 手动 2 次 + 定时 2 次 + 外部 24 次 ≈ 31 次 × 6 | **≈ 186 次/天** |
| 折算到每小时 | 186 / 24 | **≈ 8 次/小时/token** |
| 6 用户合计 | | **≈ 1,100 次/天** |

对比 Canvas 限流（社区经验值约 700 次 / 10 分钟 / 用户），**用量低两个数量级，安全**。这也是"前期可以放宽频率"的底气来源 —— 但**熔断上限仍然要写死**，因为失控的循环比正常用量危险得多。

## 6. 限流与节流规则

1. **串行执行**：所有 Canvas 请求排队串行，禁止 `Promise.all`。违反会触发并发惩罚，反而更慢。
2. **读响应头**：每次响应记录 `X-Rate-Limit-Remaining`。若剩余值低于单次同步剩余所需请求数，**立即停止本次同步**，标记 `partial`，剩余课程下次再补。
3. **三级熔断**：单用户单日 300 请求上限；单次同步 20 请求上限；单课程 3 页分页上限。任一触发 → 停止并标记 `partial`（**不是 `failed`**，因为已成功的部分是有效的）。
4. **节流是服务端的**：前端刷新按钮可以在 UI 上置灰，但**服务端必须独立校验间隔**，不接受仅靠前端节流。

## 7. 变更检测与写入策略

| 场景 | 判定 | 动作 |
|---|---|---|
| 新作业 | `source_id` 在库内不存在 | 插入，`status='pending'` |
| 内容有变 | `external_updated_at`、`due_date`、`title` 任一不同 | 更新这些字段，**其他字段不动** |
| 无变化 | 全部相同 | **不写库、不刷 `updated_at`**（见下方 `last_seen_at` 的取舍） |
| 外部已删除 | 本次同步中未出现，且 `source='canvas'` | 软删除 `is_deleted=true`（**不物理删除**，老师误删后恢复很常见） |
| 删除后又出现 | 已软删除的行本次又拉取到 | **恢复**（`is_deleted=false`），不是新建一行 |
| 拉取不完整 | 翻页被熔断截断 / 中途失败 | **不做任何删除** —— 不完整的结果集会把没拿到的行误判成"外部已删除" |
| deadline 变更 | `due_date` 发生变化 | 更新 + 计入 `sync_runs.tasks_updated`；**Phase 0 不主动通知**（Phase 1 引入变更提醒） |

**写入铁律（对应 S3 原则）**：

```ts
// ✅ 正确：只覆盖外部源拥有的字段
await updateTask(existing.id, {
  title: incoming.name,
  dueDate: incoming.due_at,
  externalUpdatedAt: incoming.updated_at,
  lastSeenAt: now,
});

// ❌ 禁止：整行 upsert —— 会把用户标记的 status='done' 打回 pending
await upsertTask(incoming);
```

> "我明明勾了完成，第二天又变回未完成" —— 这是这类应用最常见的体验 bug，根因就是整行 upsert。

**`last_seen_at` 的一处取舍（P0-2-5 落地时发现，别当 bug 修）**：
本表写着"无变化时仅更新 `last_seen_at`"，但 `tasks` 上有 `trg_tasks_updated_at` 触发器，
**任何 UPDATE 都会连带刷新 `updated_at`** —— 于是"每次同步刷 last_seen_at"与"不刷 updated_at"
在物理上不可兼得。实现选择了后者：无变化的行一次都不写，
`last_seen_at` 的实际含义退化为"最后一次被观察到**发生变化**的时间"。
删除判定不依赖它（依赖"本次完整拉取中缺席"），所以不影响功能，只是字段注释比实际多说了一点。

## 8. 失败处理与重试

| 错误 | 重试？ | 动作 |
|---|---|---|
| 网络超时 / 连接错误 | ✅ 最多 2 次，退避 **1s → 4s**（指数 + 抖动） | 仍失败 → `partial` |
| 5xx | ✅ 最多 2 次，同上 | 仍失败 → `partial` |
| **429 限流** | ✅ 最多 1 次 | 读 `Retry-After` / `X-Rate-Limit-Remaining` 后退避；再失败 → `partial`，剩余下次补 |
| 404 | ❌ | 跳过该资源，不影响本次同步其他部分 |
| **401 / 403（凭证失效）** | ❌ **绝不重试** | 立即 `canvas_credentials.status='error'`，UI 引导重新生成 token。**停止该用户的定时同步**，不浪费请求 |
| 解析异常（JSON 结构不符预期） | ❌ | 记录 `error_message`，标记 `failed`。**不允许吞掉异常后当作"没有作业"** |

> 🔴 **上表的 401/403 规则只对「作业」生效 —— 资料区（P0-3-19）是唯一例外，且必须例外。**
> 实测（2026-09-18，Steven 真账号）：**14 门课里 8 门** `/files` 返回 **403**
> （Assessment Pilot / GBA / Hazing Prevention / PartySafe / SHAPE …），
> 而同一个 token 打它们的 `/assignments` 与 `/folders` 全是 200 —— **这些课压根没开 Files 区**。
> 若把这条 403 也判成"凭证失效"，就会立刻 `markCredentialFailed` 并停掉该用户全部同步：
> **凭证明明有效，却被一门没开 Files 的课连坐。**
> 故：`lib/sync/canvas-files.ts` 里的 401/403 **只跳过那门课，绝不写凭证状态**；
> **凭证有效性只由作业同步判定**（作业跑在最前面，token 真失效时轮不到资料区）。
> 同理，资料区的失败不进 `failures`、不改同步 `status`，只记在 `SyncFileSummary.error`。

**课程级隔离**：单门课程失败不得影响其他课程。整体状态判定：全部成功 = `success`；部分成功 = `partial`；全部失败 = `failed`。

**禁止空 catch**（见 `CodingRules.md` 第 7 节）。捕获异常必须：记录日志 + 写入 `sync_runs.error_message` + 给出用户可见状态。

## 9. 失败可见性（UI 契约，硬性）

数据来自 `courses.last_synced_at` / `sync_status` / `sync_error` 与 `sync_runs`。

| 状态 | 必须展示 |
|---|---|
| `success` | "最后同步于 {相对时间}"（如"3 分钟前"） |
| `partial` | "N 门课已同步，M 门失败" + 失败课程名 + **重试按钮** |
| `failed` | **失败原因（人话，不是堆栈）** + 上一次成功时间 + **重试按钮** |
| `never` | 引导连接数据源，不显示任何"暂无任务"（否则用户会误以为这周没作业） |
| 陈旧（>24h 未成功） | **总览页顶部警告条**："数据可能不是最新的，最后同步于 X 天前" |
| 凭证失效 | 全局横幅："Canvas 连接已失效，请重新生成 token" + 直达设置页 |

**明令禁止**：
- ❌ 隐藏"最后同步时间"
- ❌ 同步失败后继续展示旧数据且不作任何提示
- ❌ 用"暂无任务"掩盖"从未同步成功"

> 静默的旧数据比明确的错误更危险。**错误信息会让人警惕，而过期的正确数据会让人放心** —— 后者才是错过的 deadline 的来源。

**P0-2-7 落地说明（2026-09-05）**：

判定与文案全部收在 `lib/sync/status.ts`（纯函数），顶部状态条与课程卡片**共用同一套判定**，不会出现两处说法打架。

| 本节条目 | 落地情况 |
|---|---|
| `success` 显示相对时间 | ✅ 状态条一行「Canvas 已于 X 同步」+ 卡片一行「Canvas 已同步 · X」 |
| `partial` 显示"N 门已同步，M 门失败" + 课程名 + 重试 | ✅ 按课程状态聚合（本节说的 `partial` 在 `courses` 上没有对应列）；失败课名列前 3 个 + "等 N 门" |
| `failed` 显示原因 + 上次成功时间 + 重试 | ✅ **分级**：凭证不可用 → 「去重新连接 Canvas」（**不给重试**，重试也不会成功）；凭证可用 → 重试 + "会自动重试" |
| `never` 引导连接数据源 | ✅ 状态条「Canvas 作业还没同步过」+ 立即同步按钮 |
| 陈旧 >24h 顶部警告 | ✅ 另有「有课从未成功过」也走同一档（缺数据比数据旧更严重） |
| 凭证失效全局横幅 + **直达设置页** | ⚠️ **偏离**：设置页属 P0-3-2，改为链到**第一门失败课程的详情页**（那里有重新连接表单，见 `canvas-link.tsx`） |

> 🔴 **`last_synced_at` 的语义在 P0-2-7 被修正为「最后一次成功同步」**（此前失败也写该列）。
> 不改这一点，"上一次成功时间"这一列根本无从展示 —— 失败会把成功时间覆盖成失败时刻。
> 详见 `Database.md` 3.2。

## 10. Token 生命周期与过期提醒

Canvas 学生 token 的过期时间是**强制必填**的（"+ New Access Token" 弹窗 Expiration date + Expiration time 均带 `*`），当前上限 **90 天**（2026-09-04 P0-2-1b 实测，弹窗原文 "Maximum expiration is 90 days."）。因此：

| 阶段 | 状态 | 系统行为 | 用户看到 |
|---|---|---|---|
| 正常 | `active` | 正常同步 | 无提示 |
| T-14 天 | `active` | 开始提醒（T-14 / T-7 / T-3 / T-1 / 当天） | 应用内横幅，可关闭 |
| 已过期 | `expired` | **跳过定时同步**（不浪费请求）；打开应用时提示 | 横幅 + 引导重新生成 |
| 调用报错 | `error` | 停止同步 | 横幅 + 引导重新生成 |
| 用户撤销 | `revoked` | 停止一切同步，删除加密凭证 | 确认提示 |

- **提醒基于用户实际填写的 `expires_at`**（强制必填，库内必有值）。提醒窗口 T-14 / T-7 / T-3 / T-1 / 当天（见下表）按 `expires_at` 倒推。
- 用户提供新 token → `status='active'` → **立即触发一次同步**（不要等下个周期）。
- **Phase 0 不做邮件提醒**（应用内横幅足够，6 人规模）。邮件留到 Phase 1 与通知系统一起做。

## 11. 降级阶梯

出问题时不二选一地"能用/不能用"，而是逐级降级，**每一级都让用户清楚知道自己在哪一级**：

| 级别 | 条件 | 能力 |
|---|---|---|
| L0 完整同步 | 全部正常 | 全部课程的最新作业 |
| L1 部分同步 | 部分课程失败 | 成功课程正常，失败课程标注 |
| L2 仅主扫描 | 逐课程请求持续失败 | 只用 `upcoming_events`，覆盖全部课程但字段精度略低 |
| L3 iCal 兜底 | PAT 不可用（学校关闭入口 / 被撤销） | 只读日历事件，拿到标题 + 时间 + 课程名（**Plan B，见 ADR-002**） |
| L4 仅静态 | 无任何数据源连接 | syllabus 解析结果 + 手动任务仍可用，顶部明确提示"数据源未连接" |

L4 不是失败态 —— **syllabus 解析的价值独立于同步存在**，这也是 Phase 0 把 M1 排在 M2 前面的原因（见 `Roadmap.md`）。

## 12. 数据源适配器抽象（为 Phase 1 多源铺路）

Steven 明确的内核要求包含 Canvas、CalCentral、Google Calendar 及课程专用网页。Phase 0 只接 Canvas，但接口从第一天就按多源设计：

```ts
// lib/sync/types.ts
interface ExternalTask {
  externalId: string;          // 源侧唯一 ID → tasks.source_id
  courseExternalId: string;    // 源侧课程 ID → courses.canvas_course_id
  title: string;
  dueAt: string | null;        // ISO 8601，null = 未知
  externalUpdatedAt: string | null;
}

interface DataSourceAdapter {
  kind: 'canvas_pat' | 'canvas_ical' | 'google_calendar' | 'course_page';
  validate(): Promise<'ok' | 'expired' | 'invalid'>;
  fetchTasks(): Promise<ExternalTask[]>;   // 内部自行保证串行与限流
  supportsDetail: boolean;                 // 能否提供 updated_at 等详情
}
```

Phase 0 实现：**`canvas_pat`**——P0-2-1 已实测确认 bCourses 学生 token 入口可用（2026-09-01，Steven）。
`canvas_ical` 适配器**不在 Phase 0 实现**，保留为长期 Plan B（L3 降级）。
新增数据源 = 实现此接口 + 在 `tasks.source` 枚举加一个值，**不动表结构**。

> CalCentral 按 ADR-007 **明确不做**（高风险、易碎、投入产出比差）。ADR 未被推翻前，不允许以"内核要求多数据源"为由把它加回来。

## 13. 可观测性与调频依据

Phase 0 不搭监控系统，**每周人工看一次 `sync_runs` 表**即可。要回答三个问题：

| 问题 | 查什么 | 说明 |
|---|---|---|
| 有没有人从来没同步成功过？ | `sync_runs` 中无 `success` 记录的用户 | 优先级最高，直接问用户 |
| 哪门课在反复失败？ | `sync_error` 按课程聚合 | 可能是权限或课程类型异常 |
| **轮询频率该不该调？** | **变更率** = 有变更的同步次数 / 总同步次数 | 见下 |

**调频规则**（ADR-005「前期宽松、后期收紧」的落地）：

- 变更率 **< 5%** 且无用户抱怨 → 说明轮询在空转，**降频**（T4 从 60 分钟放宽到 120-180 分钟）。
- 变更率 **> 20%**，或用户反馈"deadline 变了 Tempo 没及时告诉我" → **提频**。
- **Phase 1 引入自适应**：单门课程若有 deadline 在 72 小时内，该课程自动提频；假期自动降频。

**不要凭感觉调频** —— 这也是 `llm_runs` / `sync_runs` 从第一天就要埋点的原因。

## 14. Phase 0 同步范围

**同步三类带结构的数据**：

1. **带 due date 的作业（assignments）** —— 主同步目标（§4 Pipeline）。
2. **Canvas 公告（announcements）** —— **2026-09-17 晚 Steven 拍板纳入 Phase 0（ADR-021），原 Non-Goal 撤销**。批量端点 `GET /api/v1/announcements?context_codes[]=course_…` + **显式两端日期**（**绕过 `end_date` 默认 +28 天陷阱**，见下）+ **窗口起点跟锚点走的动态滚动窗口**（ADR-023：起点 = 上次成功同步那天，常态"当天 + 昨天"，断更自动回补，14 天上限）幂等（P0-3-25）。公告 `message` 是 HTML → 必须剥标签/消毒，禁 `dangerouslySetInnerHTML`（stored XSS）。落点规则：**有结构化落点（quiz/exam/作业变更）→ 进消息栏出可确认提案**；**无结构化落点（如 office hours 变更、本周课取消）→ 只给「知道了」回执，不写任何字段**（Steven 拍板去掉 OH 结构化落点，避免造一个没人维护的 OH 模型）。

**🔴 进站口径：落点判定不只决定按钮文案，还决定"要不要合并"（2026-09-18 Steven 拍板，ADR-022）**

- **有落点 → 逐条进消息栏**：各自一条消息，按钮「确认」，applier 会真的写 `exam_dates` / `grade_components`。
- **无落点 → 全部合并成一条摘要**：标题如「6 门课的 40 条通知类公告」，气泡里先给 3 行预览，可展开逐条看**标题 + 课程名 + 发布时间 + 原文链接**，按钮「知道了」（一个字段都不写）。

实测依据（2026-09-18，真账号 14 天窗口）：**48 条公告 / 40 条无落点**。每条各进一次 = 用户要点 48 次「知道了」，与 ADR-016「用户操作量趋零」直接冲突；合并后消息栏只新增 **9 条**（8 逐条 + 1 摘要），而用户**一条都没漏**（不合并那条路会把"office hours 改了"这类在意的事藏起来，代价更大）。摘要**按轮**生成（一轮同步一条），持续收通知就在时间线上积累多条 —— 每条代表"那一轮老师发了什么"。

**🔴 `end_date` 陷阱（P0-3-25 必读）**：`GET /api/v1/announcements` 默认只回**最近 14 天**；更坑的是 `end_date` 默认 = `start_date + 28 天`。只传 `start_date=2026-07-20` → 实际窗口 `[7/20, 8/17]`，**把最近一个月的公告全部排除**（实测 2 条 vs 逐课端点 71 条）。要"从某天到现在"**必须两个参数都显式传** + 按公告 id 去重 + 动态滚动窗口（幂等、漏跑自愈）。

**🔴 公告要点（AI 总结）也属于 §14 范围，但走独立通道（2026-09-18 Steven 拍板，ADR-024）**

公告原文几乎全是英文，用户要在几秒内判断"这条要不要管"。于是给**消息**加一层中文要点，但**不塞进同步路径**：

- **懒生成 + 落库缓存**：`message_summaries`（主键 `(message_id, locale)`），触发点是**打开消息栏之后**（`POST /api/v1/messages/summaries`）。首屏画服务端已缓存的，缺的静默补齐 —— 同步不承担模型延迟，用户不用多点任何东西。
- **只对"仍待处理"的公告消息生成**：已处理的只剩一行回执，要点没有位置（也避免为历史消息花钱）。
- **进站（同步）与要点（读取）彻底解耦**：这一条保证"模型挂了不影响消息栏可用"，以及"定时同步（service role、无 cookies）不必去写依赖会话的 `llm_runs`"。
- **覆盖不全要如实标**：一条消息可能挂 40 条公告，喂进模型的正文有预算 → 界面写「基于最新 20 条 / 共 40 条」，绝不假装全总结过。
- **语言是入参**（`locale`）：先出中文、专有名词保留英文；英文版上线时加一行数据即可，不需要迁移、也不会互相覆盖。详见 ADR-024。

**🔴 窗口是动态的（ADR-023，2026-09-18 晚收窄）**：上表的 48 条是**固定 14 天窗口**的产物，会把历史存量一次灌进消息栏（Steven 验收原话"抓的有点太多了"）。但**不能改成只抓当天**：cron 在 UTC 10:00 / 22:00 跑，15:00 那轮之后（如 17:00）老师发的公告，次日那轮的"当天"已是次日 → **永久丢失且无任何提示**。正解是起点 = **上次成功同步那天**（`courses.last_synced_at` 取 min，`lib/canvas/announcements.ts` 的 `announcementWindow`）：

| 情形 | 窗口 |
|---|---|
| 今天已同步过（常态） | 昨天 → 明天（2 天） |
| 断更 N 天（N ≤ 14） | N+1 天前 → 明天，自动回补 |
| 从没同步过（刚关联 Canvas） | 昨天 → 明天（**刻意不拉历史存量**，看历史走每条消息的「原文 ↗」） |
| 断更 > 14 天 | 夹到 `ANNOUNCEMENT_WINDOW_MAX_DAYS = 14` |

实测：14 天窗口 48 条 → 本轮动态窗口 **5 条**（少 43 条），且这 5 条全在账上 → **本轮真正新增 0 条**。窗口经 `SyncAnnouncementSummary.windowStart/windowEnd` 透出，便于对账。

⚠️ 收窄窗口后 `end_date` 陷阱**不再造成漏数据**（起点是昨天时，`[昨天, 昨天+28]` 照样覆盖今天），但 `announcementsPath()` 仍强制两端都传 —— 它是防将来改窗口时的地雷，且在线探针仍用 14 天窗口复现它作为历史证据。

**仍明确不同步（Non-Goals）**：

- ❌ 成绩（grades / submissions 的权威分）—— 3-17 只**读** `submission.score`/`points_possible` 展示，不写、不同步权威课程总分（Canvas `enrollments.grades` 对本人 null）。
- ❌ 讨论区（discussions，非 announcement 部分）
- ❌ 课程文件**内容** —— P0-3-19 只抓**元数据**（文件名/文件夹/外链），不下载内容。

**🔴 第三类：Canvas 文件元数据（P0-3-19，2026-09-18 落地）**

只建**目录**，不下载内容：`/courses/:id/files` + `/folders` → `course_files` 表 →
课程页「资料」区按 Canvas 文件夹结构分组、点开外链回 Canvas。要点：

- **只存目录**：表里没有任何一列能装文件内容。3-20（大纲漂移）/ 3-23（practice test）
  才按需 `GET` 那**一个**文件，用 `modified_at` 做差量。
- **每课 2 个请求，走 24 小时独立节奏**（手动刷新除外）—— 单次同步只有 20 个请求预算，
  每轮都扫会把作业挤掉。字段是 `courses.files_scanned_at`（**扫描节流**，非新鲜度承诺）。
- **顺序是先 `/files` 后 `/folders`**：403 的课（实测 8/14）在花第二个请求之前就收工。
- **学生看不见的不索引**：locked / hidden / `*_for_user` 的文件，以及落在不可见文件夹里的
  （实测 Chem 1AL：55 个文件夹里 24 个 hidden）。⚠️ Canvas 的 `hidden` 未隐藏时是 **`null` 不是 `false`**。
- **外链必须拼**：`https://{domain}/courses/{cid}/files/{fid}`（实测 200）。
  Canvas 返回的 `url`（`/files/{id}/download?...&verifier=...`）是**能力凭据（capability URL）**
  —— **不带任何 `Authorization` 头直接 GET 也 200 返回文件本体**（2026-09-18 实测修正本条原文
  的「需 Bearer、点开 401」），故**既不落库也不下发浏览器**，只在服务端当次请求内用完。
  见 `CodingRules.md` §10.1、**ADR-026**。
- **删除判定只在拉取完整时做**（§7 同一条铁律）。
- ❌ 花名册

理由三条：① 最小权限原则（ADR-002 / ADR-008）—— 请求的数据越少，ToS 暴露面越小；② 少一处数据少一处合规义务；③ Phase 0 只接"有结构落点"的数据，无落点的只给回执。

等到 Phase 1 走正式 OAuth 时，再按 scope 逐个评估是否放开成绩 / 讨论区。

**🔴 第四类：大纲漂移检测（P0-3-20，2026-09-18 落地）—— 同步零下载，读内容全在「打开消息栏之后」**

老师改 syllabus（改期 / 加考试 / 调成绩构成）是「用户不走运才撞上」的信息。本类让 Tempo 自己发现它，但**绝不自动改任何字段**。

- **同步侧只做三件事：零 Canvas 请求、零模型调用、1 个 SELECT** —— 从 `course_files` 里挑出 syllabus 文件 → 与 `courses.syllabus_seen_modified_at` 比 `modified_at` → 变了才建一条 `type='syllabus_drift'` 的消息（`driftStatus='pending'`）。挂在 Pipeline **第 9 步**、排在资料索引之后（读的就是 3-19 的产物）。
- **🔴 真正的文件读取发生在用户打开消息栏之后**（`POST /api/v1/messages/drift` → 下载那**一个**文件、抽文本、调模型 diff）—— 这是 **ADR-026** 的边界：**批量/后台路径零下载，用户触发路径才读内容**。原文/全文**不落库、不落盘、不进日志**，只落模型产出。卡面原文写的是「**同步时**按需抓 syllabus 文件」，与 ADR-026 冲突；且定时同步跑在 **service role + 无 cookies** 下写不进 `llm_runs` 审计（实测 `cookies was called outside a request scope`，会打穿 ADR-003）。**2026-09-18 Steven 拍板改为懒补**（范式同 **ADR-024**）。
- **首次核对 / 换文件 = 只记基线，不提案**（`baseline`）：否则 6~13 门课首次同步会各塞一条纯噪音；换文件时两份文档没有共同锚点，「变了」在语义上不成立。
- **三条「不」**：**不下载**（同步侧）｜ **不猜**（`size_bytes === null` 不当候选、`modified_at === null` 不报变更）｜ **不诬告**（只认名字含 syllabus/大纲 的文件，**不认 `outline`/`schedule`** —— 那是另一份文档，说它"变了"是诬告）。
- **差量锚点是「文件版本」不是「核对时间」**：`courses.syllabus_seen_modified_at` 存的是 `course_files.modified_at`（**内容变更看 `modified_at`，不是 `updated_at`**），所以两值可比；存的不是"我们上次什么时候查的"。
- **不自动覆盖**：提案只能落到 `source='syllabus'` 且 `is_confirmed=false` 的行 —— 已确认的考试日期是权威源（**ADR-004 / ADR-015**），**在 applier 里就不在可写范围内**；且 applier 只照做提案里就地的 `writable` 判定、不重判。撤销必须按**结构化旧值快照**还原（漂移含 update，不能按 id 删）。
- **扫描件 PDF 提取不准 → 提案标 `confidence='low'`，低置信度不许一键接受**（卡面边界）。
- **不占同步请求预算**：整类在同步侧 0 个 Canvas 请求；按需路径的下载不计入 §5 的 20 请求预算。
